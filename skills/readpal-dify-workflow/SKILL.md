## 🔑 首选路径：起可见窗口 → 人工登录 → 复用登录态（2026-09-18 打通）

```bash
python3 tools/launch_dify_chrome.py 9237     # 独立 profile，弹可见窗口，停在登录页
#   → 让 Bryan 在弹出的窗口里登录 cloud.dify.ai（就是他改工作流那个账号）
curl -s http://127.0.0.1:9237/json/list | grep -o '"url": "[^"]*"'   # 确认已是 cloud.dify.ai 而非 /signin
DIFY_CDP_PORT=9237 node tools/dump_full_draft.mjs <app_id> /tmp/full.json
```

⚠️ **端口别乱挑**：本机常驻若干 **headless** Chrome（9224 / 9231 上就是 `localhost:8899` 之类
别的任务）。踩过的坑：脚本探测到端口被占就「复用」，结果 attach 到 headless 实例上 ——
没有窗口、没有登录态，一直空等人登录。先探：

```bash
for p in $(seq 9232 9245); do curl -s --max-time 1 http://127.0.0.1:$p/json/version >/dev/null || echo "FREE $p"; done
curl -s http://127.0.0.1:<port>/json/version | grep -i headless   # 命中就换端口
```

**判据**：`/json/version` 的 `User-Agent` 含 `HeadlessChrome` ⇒ 无窗口无登录态，别用。

> 登录态存在**独立 profile** `/tmp/chrome-dify-<port>` 里，不碰用户日常 Chrome，也不影响
> 别的调试实例。会话失效时（换设备登录会把旧 token 顶掉）让 Bryan 在这个窗口里重登一次即可。

## 🔑 兜底路径：没有调试端口时，复用本机 Chrome 的 cookie（2026-09-18 实测打通）

**症状**：CDP 端口里只有本地页面、没有 `cloud.dify.ai` 页签（`--no-startup-window` 起的新 profile 没有登录态），
`dump_draft.mjs` / `dify_push_graph.mjs` 全部拿不到图。

**别急着重登控制台 —— 先复用本机 Chrome 已登录的 cookie**：

```bash
python3 tools/dify_console.py          # 自检：打印 cookie 名 + 试调 /console/api/apps
```

- 原理：读 `~/Library/Application Support/Google/Chrome/Default/Cookies`（**先 copy 到临时文件再读**，
  否则 sqlite 被 Chrome 锁住），用 `security find-generic-password -w -s "Chrome Safe Storage" -a Chrome`
  取口令 → `PBKDF2-HMAC-SHA1(pw, "saltysalt", 1003, 16)` 派生密钥 → `openssl enc -aes-128-cbc`
  解 `v10` 前缀的 `encrypted_value`（IV = 16 个空格；Chrome 127+ 明文前 32 字节是 `sha256(host_key)`，要剥掉）。
- 调用时**两个头一个都不能少**：`Cookie:` 全量 + `X-CSRF-Token: decodeURIComponent(__Host-csrf_token)`。
- `POST /console/api/refresh-token` 的 refresh token 也是过期的（跨设备登录会顶掉）→ **401+403 同时出现就是会话真死了，
  只能让用户在本机 Chrome 重新登录一次**，然后立刻重跑 `dify_console.py` 即可续上，无需调试端口。

> 判断会话是否还活着：`__Host-access_token` 是 JWT，直接调 `/console/api/apps?page=1&limit=5` 最省事。
> 「Token has expired」= 过期；「Invalid refresh token」= 彻底失效，必须人工登录。

## 控制台 API 要点

- **鉴权**：cookie `__Host-csrf_token`（`decodeURIComponent` 后放 `X-CSRF-Token` 头）。
  **401「Invalid Authorization token」十有八九是漏了这个头**，不是登录过期 —— 别急着重登。
  页面久不刷新会丢 token，`--goto` 重新加载即恢复。
- **改图**：`POST /console/api/apps/{app_id}/workflows/draft`，
  body = `{graph, features, conversation_variables, hash}`。
  - ⚠️ **`features` / `conversation_variables` 必须带原值**：先用 `dump_full_draft.mjs` 拉**完整**草稿，
    在它的 `graph` 上定点改，再整体推回。只拿 graph 去推 → 这两项以 `undefined` 送出，
    **应用的 features（文件上传 / 语音 / retriever 等）会被清空**。
    推完务必回读比对 `features` 是否与推前一致。
  - ⚠️ **不要带 `environment_variables`** → `extra_forbidden`。
  - ⚠️ **乐观锁**：必须回传当前 `hash`（先 GET draft 拿）。
- **试跑 draft**：`POST /console/api/apps/{app_id}/workflows/draft/run` → **SSE 事件流**
  （`workflow_started` / `node_started` / `node_finished` / `workflow_finished`）。
  改 draft **不影响线上**，可反复试，满意再发布。
- **查运行记录**：`GET /console/api/apps/{app_id}/workflow-runs?page=1&limit=12`
  —— 用来判断「请求到底有没有进执行引擎」。
- **查发布版本历史**：`GET /console/api/apps/{app_id}/workflows` → `{items:[{id, version,
  created_at, marked_comment, graph}]}`，**每个历史发布版本都带完整 graph**。
  ⇒ 「这改动是什么时候进去的 / 线上以前长什么样 / 是不是我这次改坏的」**直接查它逐版比对，
  不要靠推理**。实测用它把「`level` 入参格式不匹配」的责任归属钉死在 09-10 那次发布上。
  （注意与 `/workflows/draft` 区分：前者是版本历史，后者是当前草稿。）
- **查插件支持的模型参数**（只读，强烈建议先跑）：
  `GET /console/api/workspaces/current/model-providers/{provider}/{provider_id}/models/parameter-rules?model={model}`
- **发布**：`POST /console/api/apps/{app_id}/workflows/publish`，body = `{marked_comment}`。
  - ⚠️ **`marked_comment` 上限 100 字符**，超了报 `400 invalid_param / string_too_long`
    （实测踩到，130+ 字的备注直接被拒）。工具 `dify_publish.mjs` 没有截断保护，**写备注自己数一下**。

## 🔴 九个静默失败的坑（都实测踩过，症状极难定位）

### 1. 变量可达性 —— 变量必须在「执行路径上」才存在

Dify 运行时严格校验。引用 `#nodeX.var#` 时，**必须有一条从 `nodeX` 到引用者的路径**，
否则报 `Variable #nodeX.var# not found`。

变量引用写在**三处**，第三处最隐蔽：
1. `variables[].value_selector`
2. `outputs[].value_selector`
3. **LLM 节点的 `prompt_template` 文本里的 `{{#node.var#}}`**

### 2. 没有入边的节点永远不会执行，而且可能不报错

Dify 的执行是**从 `start` 出发的可达性驱动**。新增节点若没有一条从 `start` 可达的入边，
**永远不会被触发**，工作流可能**直接跑完且 status=succeeded**。

> 必须有一条静态断言：「每个非 start 节点都从 start 可达」。
> 这两条一起写进 `validate_graph()`，并用**对照实验**验证校验器真的能抓住
> （删边/改错引用/造环/删输出变量，四组都要被捕获）。

### 3. `thinking` ≠ `enable_thinking` —— 参数名写错会被静默丢弃

Dify 硅基流动插件的思考开关是 **`enable_thinking`**（boolean，默认 false）。
写成 `thinking` **不报错、不提示，直接丢弃** → 模型按 SF 默认**开着思考**跑。

实测（`DeepSeek-V4-Flash`，400 词长文，`max_tokens=1600`）：

| 参数 | 耗时 | completion tokens | reasoning |
|---|---|---|---|
| 无参数（SF 默认） | 54.0s | 10641 | 30335 字符 |
| **`enable_thinking: false`** | **8.0s** | **533** | 0 |

→ **慢 6.75 倍、token 多 20 倍**。GEN 要出 2.5 万 token，开着思考会拖到十几分钟。

**症状极具迷惑性**：service API 返回 **HTTP 200 但 SSE 连续几分钟零字节**
（连 `first-byte` 都没有），看起来像"网络问题"或"Dify 挂了"。

> 该插件只认这 9 个参数：`temperature` `max_tokens` `top_p` `top_k`
> `frequency_penalty` `response_format` `json_schema` **`enable_thinking`** `reasoning_effort`。
> 顺便：SF 原生 API 直接传 `thinking=false` 会 **HTTP 400**。

### 4. 知识库检索「英文 query → 中文文档」0 命中

`knowledge-retrieval` 节点的 `query_variable_selector` 若指向**英文素材文本**，
而知识库是**中文标准文档** → 向量检索跨语言失配，`result` 恒为**空数组**，
**整条参考路径是死的，且不报错**。

**解法**：在检索节点前插一个 code 节点，输出**固定中文检索意图词**
（如「分级标准 词数 蓝思 句长 对照表」）。实测召回 8 段，score 0.68–0.73。

### 5. `blocking` 有约 120s 网关硬超时

长工作流（>120s）用 `response_mode: "blocking"` 会**直接 504**（实测 GEN 145s 时 504）。
必须用 `streaming`（实测 184.7s 的工作流正常返回，首字节 1.1s）。

> 前端调用同理：ReadPal 的 GEN 已改 SSE，并按 `node_finished` 显示「已完成 N 个节点」。

### 6. `select` 类型入参**不能传空字符串** —— 传了工作流秒退

即使该变量 `required: false`，传 `""` 依然会报
`xxx in input form must be one of the following: [...]`，
且**工作流 0 个节点完成就结束**（`{"done":true,"nodeFinished":0}`），看起来像"什么都没跑 / 网络问题"。

> **正确做法：整个省略该键**（`{"material": "..."}`），不是传空串、也不是传 `null`。
> **副产品**：这个报错会把 12 个合法选项**全列出来** —— 可以当成
> 「新 start 节点是否真的生效」的**反向验证手段**，非常好用。

#### 6.1 同族的第二个触发条件：**传了枚举里没有的值**（2026-09-14 实测报障）

同一个报错，另一条完全不同的成因：**前端把内部主键当对外枚举值发**。

| 侧 | 格式 | 出处 |
|---|---|---|

### 7. 控制台 CSRF cookie 短时失效 → 401，刷新页面即恢复

`__Host-csrf_token` 存续期不长，久不操作会只剩营销 cookie
（`hasCookie: false, csrfLen: 0`），此时所有 console API 全部 **401**。

**这会大概率不是登录过期 —— 别急着重登**，跑一次
`node dify_cdp.mjs --goto="https://cloud.dify.ai/apps" --wait=10000` 重新加载页面即恢复。

⚠️ **但 401 有两种，必须先用一条命令分清楚**（2026-09-22 实测踩坑）：

```js
// 在 Dify 页签里 eval：
document.cookie.split(';').map(s=>s.trim().split('=')[0]).join(', ')
```

| 看到的 cookie | 结论 | 处置 |
|---|---|---|
| 有 `__Host-csrf_token` / access_token | CSRF 短时失效 | **刷新页面即恢复**，别重登 |
| **只剩第三方 cookie**（cookieyes / _ga / AMP_*） | **登录态彻底没了** | **只能人工重新登录**，任何刷新都无效 |

**🔴 根因（2026-09-22 定位并修复）：profile 放在了 `/tmp`。**
`launch_dify_chrome.py` 原来用 `--user-data-dir=/tmp/chrome-dify-<port>`，
而 macOS 会在重启/清理时删 /tmp ⇒ **cookie 连同登录态一起消失**，
表现为「昨天还能推图，今天所有 `console/api/*` 全 401」。

**已修**：`PROFILE` 改到 `~/.workbuddy/chrome-dify-<port>`。**别再改回 /tmp。**
（改 profile 位置后必须**重启该 Chrome 实例**才生效；新 profile 是空的，要重新登录一次。）

**另：查余额/验通道不用开控制台会话** —— 拿一个**已发布** App 的 API Key 直调
service API 即可（几十秒出结果，且不受登录态影响）：

```bash
curl -s -X POST https://api.dify.ai/v1/workflows/run \
  -H "Authorization: Bearer app-xxxx" -H "Content-Type: application/json" \
  -d '{"inputs":{...},"response_mode":"blocking","user":"probe"}' | head -c 500
```

返回 `{"data":{"status":"succeeded",...}}` = 通道与余额都正常；
`402 Insufficient Balance` = 渠道余额耗尽；`{"code":"invalid_param","message":"Workflow not published"}` =
**App 还没点「发布」**（API Key 调不通未发布的工作流，这一点很容易误判成密钥问题）。
**沙箱里 `ps` / `pkill` 都被限制**，关不掉既有 Chrome 实例 —— 直接换一个新端口启动即可，
不必纠缠清理旧实例。

**同一根因还会以 `TypeError: network error` 出现**（不是 401，是页面执行上下文失效），
典型触发是**连着跑多个 CDP 脚本**（连续推多个 app、推完立刻跑 draft）。
实测：一条命令里连着推 GEN + MAIN **两个都静默失败**（grep 不到 `[push]` 行），
刷新后逐个推即 200。**对策：批量操作在每个关键动作前加一次 `--goto` 刷新，或拆成独立命令。**

### 8. `api.dify.ai` 偶发 Cloudflare `403 code 1010` —— 不是密钥失效

service API 三把密钥同时 `✗ HTTP 403 error code: 1010` 时，**先别怀疑密钥**。
这是 Cloudflare 机器人拦截（对 UA 敏感），**换 UA / 重试即 200**。

> 定位套路可复用：403 → 查 UA 相关 → 换 UA 复测 → 确认偶发。
> **绝对不能看到 403 就断定密钥被吊销**，否则会白改一轮配置。

### 9. 页面大小「不一致」先分字节 vs 字符

`curl` 报 677393（**字节**）而 Python `len()` 报 640391（**字符**，中文 3 字节）——
数字对不上**不代表部署漂移**。用 **md5 相同** + 内容特征串（如 `BIG_GROUPS=13`）才下结论。

## MAIN 单真源拼装（FACT ⊕ GEN）

> 全部从 start 可达、边两端存在、模型与思考开关、12 档下拉选项、无旧三档痕迹、

## 🧪 回归必须用「短 + 长」两组素材（只看一组会漏缺陷）

12 档 MAIN 有两类**方向相反**的稳定缺陷，用同一组素材测不出来：

| 素材 | 现象 | 实测 |
|---|---|---|
| **短素材**（63 词 / 4 条事实） | **高段位系统性偏短** | B2+.3 两次跑出 **646 / 648 词**（目标 900–1200），100% 可复现 |
| **长素材**（374 词 / 9 条事实） | **低段位系统性超写** + **格式漂移** | A2.2 冲到 **312 词**（上限 250）；B1.1/B1.2/B1.3 段数 **11**（规格 6） |

**两个 MUST 检查**（跑完 outputs 就能查）：

1. **段落数**：`paras_json[k].length` 是否等于规格段数（A1=4 / A2=5 / B1=6 / B2+=8）。
   模型会**把生词表当成段落**追加到正文数组末尾 —— 聚合 code 节点 `GEN_AGG_CODE` 只判"是不是数组"、
   不判长度，所以脏数据会一路透传到 `paras_json` / `para_count` / `levels_meta`。
2. **词数**：`validation_json.results[].word_count` 对硬区间，看是偏短还是超写。

**根因一句话**：`ruler()` 算的「每段 N 词 / 约 M 句」数学是对的，
但**段数是结构约束（模型严格守），每段句数是长度约束（模型守住 3–4 句就收）**，
所以最终篇幅由**素材提供的事实条数**驱动，而不是档位规格。

> 详细数据、根因定位与修复方案见仓库 `readpal/docs/11-生成质量实测与已知缺陷.md`。

### 已实施的修复（2026-09-11，A + C）

| 方案 | 位置 | 做了什么 |
|---|---|---|
| **A** | `GEN_AGG_CODE` | 内联 `PARAS` 规格段数表 → **过滤生词表行**（`^英文词[:：—–-]+中文`，单行 ≤60 字）→ 兜底过滤含 >5 中文的脏段 → **按规格段数截断** → 全部写进 **`map_warn`** → 生词表**救回 `words` 字段**不丢数据 |
| **A** | `GEN_VALIDATE_CODE` | 「语言纯净度」文案改为「正文段落疑似混入生词表/中文」+ 回传命中片段 |
| **C** | `gen_sys` | 删掉过期的「最容易犯的错是超写三成以上」；硬指标 2 条 → 3 条（新增**每段句数**）；新增「**素材不足时**允许合理背景扩写但不得编造数字/人名/机构」+「**素材过多时**低段位不得膨胀、篇幅梯度必须严格递增」；B2+ 组把区间**折算成每段硬指标** |

**效果（实测回归）**：
- ✅ 段数污染**彻底修好**：两跑 12 档段数全部等于规格；`paras_json`/`para_count`/`levels_meta` 三者一致
- ✅ `B2+.1` 超写修好（823/832 → 664/572）
- ✅ 低段位随素材膨胀修好（A1.1 111→89、A2.2 312→236）
- ✅ 短素材 `all_pass` 首次为 `true`（89/96，此前一直 false）
- ⚠️ **B2+.3 在短素材下仍偏短**（646/648 → 718，目标 900–1200）—— **确认是素材量天花板，提示词改不动**
- ⚠️ **新暴露**：长素材 A1.3 反而超写（198/上限 160）—— 引导"不许低于下限"会过冲，**改提示词时要防 overshoot**
- ⚠️ **新暴露**：A2 组语言难度不达标（A2.1 句长 7.4 vs 10–12、蓝思 133L vs 400–500L）

> **两条可复用的经验**：
> ① **"素材量 → 事实条数 → 可写篇幅"是硬耦合**。提示词只能优化到素材允许的上限，
> 想突破必须提高素材量，或者拆节点。
> ② **提示词调优会 overshoot**：把"别写短"加粗之后，低段位转头就写超。
> 每次改完必须**双素材跑两遍**，盯住"两端"而不只是失败的那一端。

## 其他易错点

- **LLM 节点的输出变量固定为** `text` / `reasoning_content` / `usage` / `finish_reason`。
  `nodeEnd` 引用时要写 `["nodeQuiz","text"]` —— **输出名可以叫 `quiz_json`，但来源变量名是 `text`**，
  这两个概念极易混淆（写成 `["nodeQuiz","quiz_json"]` → 拿到 `null`）。
- **code 节点输出类型强校验**：声明 `string` 却返回 `int` → 节点直接失败
  （`Output fact_count must be a string, got int instead.`）。
  **本地写测试台断言「输出类型 vs 声明类型」**，这类错本该本地拦住。
- **`start` 节点的 `variables` 是入参声明**，没有 `value_selector`，不参与变量引用校验。
- **无入边的节点并行执行**，Dify 按拓扑序批量推进 —— 4 个生成节点可真正并行。
- **模型吞吐必须用「并发 + 长输出」测**。单次小请求会给出严重乐观的数字
  （同一模型小请求 69 t/s、4 路并发长文只有 21.6 t/s）。
- **提示词里的"实测结论"要跟着参数一起改**。反面教材：`gen_sys` 第 183 行还留着
  「实测最容易犯的错是**超写三成以上**」，而 B2+ 组第 146–148 行写的是
  「实测本组**系统性偏短**」——**同一段提示词里两种相反引导并存**，
  是早期迭代的过期结论没清理。**改了模型/参数后，要把旧提示词里的"实测经验"重新验一遍。**
- **模型偶发输出尾逗号** → 严格 `json.loads` 直接失败（实测 `B2+.3 深写版` 1417 词那跑）。
  解析层统一加容错：`json.loads(re.sub(r',(\s*[\]\}])', r'\1', frag))`，**先严格再容错**。
- **⚠️ 同一文件的多个 Edit 必须串行，一次一个**。并行发多个 Edit 时**部分改动会被静默丢弃**，
  但**每一个都回报"成功"** —— 实测 5 处改动只落了 2 处，且生成出的 JSON 里同一个节点
  新旧值混杂（A1.1 已放宽、A1.2 仍是旧值），**静态校验器完全查不出来**。
  对策：改完**回读源文件逐处核验**（`sed -n 'Np'` 或 grep 残留旧值），再重跑生成器。
- **推送前必须 diff 线上 draft**：本地 `{fact,gen}.graph.json` 是"某个时刻"的快照，
  若它早于最近一次上线，重跑生成器会**把已上线的修复整段回退**。
  标准做法：拉 draft 存 JSON → 与本地新图逐字段比对 → **差异必须恰好等于本次改动**。
  实测命令：`node tools/dump_draft.mjs <app_id> <out.json>` + `python3 tools/diff_graph.py <线上> <本地新图>`。
- **🔴 聚合节点的 `parseJSON` 必须容错尾逗号**（2026-09-11 实测踩到，代价是**整组静默归零**）：
  模型偶发在每段数组末尾多写一个 `,`（`"…We must watch it.",\n  ],`），严格 `JSON.parse` 直接抛错
  → `parseJSON` 返回 `{}` → **该组三档同时降级成 0 段**（`para_count` 全 0、`raw_missing` 只剩一个 `A1`、
  前端就是空白文章）。**而工作流状态仍是 `succeeded`，校验器也照样给它打分（0 段不判 fail）** —— 三重掩护。
  离线脚本 `run_*` 早就有 `re.sub(r',(\s*[\]}])', r'\1', frag)`，**聚合节点当时漏了**。
  **修复要覆盖两处**：`GEN_AGG_CODE.parseJSON`（L339 附近）与 `FACT_CLEAN_CODE.parseJSON`（L935 附近）。
- **识别信号**：`map_warn` 里出现「段数不足 **0** 段（规格 N），无法补齐」+ `raw_missing` 非空
  → 一定是解析层而不是模型层的问题，先看该组的原始 `text` 有没有尾逗号 / 代码块残渣。

| 给模型的指令 | 结果 | 判定 |
|---|---|---|
| 只说"写长一点 / 要达标" | B2+.3 段数 8 → **10**、句长 22.8 → **29.5** | ❌ **加段落 + 拉长单句**，两条都是歧路 |
| 给"全篇句数预算" | B2+.3 掉到 **319 词**、句长冲到 **39.9** | ❌ 反向破坏 |
| **给"每段必须 113–150 词，段数固定 8"** | **1417 词 / 8 段严格 / 句长 25.8** | ✅ **唯一有效** |

**结论：模型无法凭感觉控全局字数，只能控"每一段写多少"。**
"每段词数预算"是本项目里对达标率影响最大的单条指令 —— 与 `ruler()` 的思路一致，
但本轮的实测把它从"建议"升级为"必须写成硬指标 + 明确禁止加段落"。

### 🔴 2026-09-22 升级：预算必须再拆成「句数 × 句长」，**能控的只有句数**

授权母稿链路（图 A：1433 词长文要压到 B2 的 468–632）真跑 8 轮，把这条规律推到了下一层：

| 提示词里的「每段预算」写法 | 实跑 | 判定 |
|---|---|---|
| 「每条要点扩成 2–3 句」（无句数上限） | 352 词 | ❌ 欠 |
| 「每段 2 句 × 20–25 词」= 41–50 词/段 | **188 词** | ❌ 更差 |
| 「固定 12 段，每段 3 句 × 13–17 词」 | 439 词 | ❌ 差 29 |
| **「固定 12 段，每段 4 句 × 10–13 词」** | **595 词** | ✅ **达标** |

**根因：模型自然句长只有 ~12 词**（与 B1 句长实测 10.1–12.4 **同源**）。
⇒「每段 41–50 词用 2 句」= 要求每句 20+ 词，**模型物理上写不出来**，必然欠写。
**这是 B2 长期不达标的真正原因** —— 不是模型"不肯写长"，是**把预算错压在句长上**。

**升级后的三条结论**：
1. 「每段词数预算」仍是达标率影响最大的单条指令（原结论成立）。
2. 但它**必须落成「句数 × 句长」两个数**，且句长要**贴着模型自然值 10–13 词**，
   用**句数**去凑每段词数：`句数 = 每段目标词数 ÷ 12`。
   按此反推：**B1 每段 28–35 词 → 2 句；B2 每段 41–50 词 → 4 句**。
3. ⚠️ **段数不能靠"清单条数"间接控制**：写「提炼 8–12 条」模型给 6–7 条，
   改「12–14 条」**还是给 7 条** —— 条数由模型对"主线"的判断决定，**给区间压不住**。
   ⇒ 改为**直接写死段数**，同时放宽"只提主线"（一条 = 一个可独立成段的信息单元，
   并明说"举例/个案/专家发言都要保留"，否则模型会删掉这些"血肉"导致没内容可填）。

### ⚠️ 另一个独立现象：**模型不会按档位调整段落长度**

同素材、同提示词、只换档位（B1 / B2），模型写出的每段词数**几乎不变**（都 ~45 词/段）：

| 档 | 要求每段 | 实测每段 | 结果 |
|---|---|---|---|
| B2 | 41–50 | 44–78 | 擦边偶尔过（上限 632÷12=52.7） |
| B1 | 28–35 | 44–52 | **必超**（上限 437÷12=36.4），实测 **0/5** |

⇒ **模型没有「档位对应段落长度」的概念**。低档（每段词数小）比高档更难达标。
调 B1/B2 时不要把两档规格并列写在一张表里 —— 实测会**串档**（B1 按 B2 的量级写）。
最好把当前档位的值用变量提到提示词最前面，只给一行。

## 🧩 节拍（beat）跨档对齐：能对齐，但节拍数不能固定

**节拍可量化**（实测）：覆盖率 = 命中语义拍数 ÷ 总数（8/8）；锚点命中率可机械比对
（B2+.3 进阶锚点 28/28、A1.1 核心锚点 17/17）。**判定单位是"两张清单"，不是"节拍"这个概念。**

**不会改原意**（实测 5 跑）：节拍覆盖 8/8、语义一致 8/8、编造 0 条。
三道拦截：必须讲的清单 + 锚点溯源（抓幻觉）+ 方向核查（抓"增加↔减少"改反）。

**意外收益**：B2+.3 平均句长**首次达标**（22.8 / 25.8）。此前四轮全部够不到下限。
原因：节拍给每一段明确了"要讲什么"，模型自然把句子写长 —— **句长问题一半是"不知道要讲什么"造成的**。

**🔴 但固定节拍数与 12 档词数规格互斥**：

- A1.1（60–90 词）实测**每节拍最少要 20–28 词** → 需要 `K ≤ 3~4`
- B2+.3（900–1200 词）实测**每节拍 71 词**（给每段预算可到 177）→ 需要 `K ≥ 8~13`
- ⇒ **无解**。12 档词数跨 20 倍，固定节拍数必然"低档塞不下、高档撑不满"。

**出路：节拍数 ≥ 段数**（A1≥4 / A2≥5 / B1≥6 / B2+≥8），跨档用
「细节拍 → 粗节拍」**多对一**映射（关系预先固定 → **可机械计算换档位置**）。
实测支持：A1.1 强制覆盖 8 节拍 → **157–192 词**（超写 74–113%）；
只覆盖 4 节拍（= 段数）→ **113 词**。

> 🔴 **2026-09-11 修正：不是「=」而是「≥」。** 实测 `节拍数 < 段数` 会触发 `distribute()` **空组**
> → 模型自己补内容 → **注水 +10～12%**、句长同时失控（33.1 vs 规格 22–26）。
> 案例：`mat_v500` 粗抽 7 条 → B2+.3（8 段）= **1291 词**；`short_s2` 粗抽 6 条 → B2+.3 = **1311 词**。
> 对照：`mat_v300_fine` 8 条 → 8 段 = **1090 词 ✅**。**这是唯一可前置机械拦截的规则。**
> 同时 ⇒ **抽取必须"按目标段数向下拆"（top-down），不能"数出条数再推上界"** —— 因为同一素材
> 换个拆分提示词，条数会从 7 漂到 14（`docs/16` §3）。

**⚠️ 切节拍的第一原则：语义拍与数字必须分开。**
把数字写进"语义要点" → 低档禁用数字时会被判"未覆盖"（实测 A1.1 只拿 3/8）。
正确切法：**语义拍不含数字**（全档必现）；**数字只作锚点**，B1+ 才要求必现。

**🔺 由上面推出的产品模型：每篇作品 = 一个档位区间 `[lo, hi]`**

- 区间**必须连续**（缺档 → 用户升档会跨 4 档跳跃，超过教研说的"相邻两档"）
- 用户在区间内自由升降；区间外**不存在**对应文章，前端按区间渲染控件范围
- **信息点条数决定区间**：抽到 8 条 → 偏上（如 `A2.3 – B2+.3`）；只抽到 4 条 → `A1.1 – A2.3`
- ⇒ "热点素材出不了 A1"不是禁止，而是**这篇的区间下界够不到 A1**

> 🔴 **2026-09-11 修正：这条也要打折。** 「信息点条数」**不是素材的固有属性** —— 它是**抽取粒度的函数**。
> 实测同一素材换拆分提示词：`mat_v500` 515 词 **7 条 → 14 条**；`mat_v400` 434 词 **7 条 → 12 条**；
> `short_s2` 198 词 **6 条 → 10 条**。
> ⇒ **不能"数出条数再推区间上界"**。正确做法是 **top-down**：先定目标档位的段数，再让抽取按该段数去拆/合。
> ⇒ 真正决定上界的是 **`max_K`（在固定拆分规则下可拆出的最大条数）**，而且**拆分规则必须先固定**，否则不可比。

**两条路径是连续谱，不是二选一**：

- 路径 A 抽 8 条细节拍，出 A1 时**合并成 4 个大意拍**
- 路径 B 只抽 4 条大意
- ⇒ **"合并后的细节拍" = "直接抽的大意"**，差别只在抽取深度
- ⇒ 工程上**不做两套系统**：一个抽取节点、输出粒度可配
- **路径 B 的真正价值**：给"信息点不足的短素材"一条出路（否则会被准入门槛拒收），是 A1/A2 产能扩容

**大意复核必须装两处**（只做事后复核只能发现错、不能防止错）：

1. 抽取节点**产出**强制输出「素材大意」（分层，N 句）→ 作为跨档对齐**基准**
2. 每档生成**之后**提大意比对 → 主线偏移则**硬失败 + 重试**，不静默放过

分工：**大意管"主线偏没偏"，节拍/锚点管"细节漏没漏"**，不可互相替代。

**浅抽取（路径 B）必须配数字/专名溯源检查**：它只有大意、没有事实清单，模型极易自编数字。

**改造点已定位**：`tools/dify_build_graphs.py` FACT 图 `nodeGrade` 现在是输出**单个** `{"level":"A1.1"}`
→ 目标是**区间** `{"lo":"A2.3","hi":"B2+.3"}` + 信息点条数；`nodeClean` 需派生 `levels_list`（区间展开）。
`LEVELS` 仍是 12 档唯一真源。设计全文见 `readpal/docs/14-素材池与档位区间设计.md`（含 R1–R7 硬规则与改造面清单）。

**区间模型顺手消解了 `docs/12` 两个悬案**：待定项 B（保词数 vs 保信息点）——有 8 个信息点的素材，A1 本就不在其区间内；
待定项 E（"其余细节宁可不写"冲突）——低档覆盖的是**全部大意拍**，不是全部细节拍。
待定项 C 的准入门槛**不按词数判**；⚠️ 但也**不能只按"数出的信息点条数"判**（条数随拆分粒度漂移，实测 7→14）。

| 检查项 | 高档（fact 基准） | 低档（gist 基准） |

| 事实一致性 | 素材关键数字一个都不出现 ⇒ **fail** | 不出现数字是**预期** ⇒ **pass**；**出现了**才 warn（可能是编造） |

## 🔴 词汇「有校验，但纠正不了」—— 解释「产出难度偏高」（2026-09-18 实测 + 当晚更正）

> ⚠️ **本节 2026-09-18 晚已更正。** 初版结论是「词汇层零校验」，那是**只核了 Dify 图**得出的

② 功能词退出统计、修表外词漏洞、阈值合并单一真源；
③ 重试时把**上一稿超纲词清单回灌**给生成（GEN 加 `avoid_words` 入参），让纠正有靶子

**🔴 回灌词必须过滤，不能把 `avoid_words` 原样丢给 LLM**

第一版实现会给出**错误指令**（「请避免使用 becoming」），实测后加了三道过滤，
逻辑全在 `backend/evp_vocab_check.py::pick_avoid_words()`：

1. **剔除功能词**（`_FUNCTION_WORDS`，约 190 词）。
   EVP 把 `by`/`over`/`around`/`should` 全标 A2 ⇒ 在 A1 档条条「超纲」，
   但 **LLM 无法避免使用语法词**，塞进去只会写出不通顺英文。
2. **剔除范文基线里的词** —— `backend/vocab_baseline.json`（**分档**，见下）。
   判据：**范文用过的词 = 教研认可的词**，不该要求规避。
   ⚠️ 必须比**词干**（`_stem_variants` 双侧降词干）。
   **别用 `lemmatize()`** —— 它只在「还原结果命中 EVP 词表」时才返回词根，
   而 `depend`/`canopy`/`accord` 这些词根**本身不在表内**，
   `lemmatize('depending')` 原样返回 `depending` → 比对必然失效。**这是第一版实测踩的坑。**
3. **基线必须分档，不能合成一份** —— 合起来 B2 范文里的难词（`habitat`/`evaporation`）
   会给 A2 也豁免掉。产出 `levels:{A2,B1,B2}`，消费侧按**本档及更低档**累积：
   `A1-`→A2（外推）· `A2`→A2 · `B1`→A2+B1 · `B2+`→A2+B1+B2（共 4935 词）。

**为什么 `A1-` 最特殊**：它的 cap 是 EVP A1（**仅 643 词族**），**比教研的 A2 范文还低**
⇒ `top`/`win`/`fan`/`side`/`care`/`heavy`/`race` 全被算「超纲」。
所以**基线过滤对 `over` 词也要做**（原文里明明在用，要求规避只会写出别扭英文）。
实测效果（NPR 体育素材）：`A1-` 规避词 **19 → 11**。
对 A2/B1/B2 几乎无影响（它们的超纲词本就在本档基线之外）。

**⚠️ 尚未修的三处判据层问题**（涉教研口径，别擅自改）：
① `check_vocab()` 的**表外词既不进分子也不进分母** → 越生僻越逃过；
② `lemmatize()` 缺 `-er → -e` 规则（`larger` 还原不出 `large`）且**与词表耦合**；
③ `A1-` 真正的瓶颈是 **cap 不是阈值** —— EVP A1 仅 643 词族，物理上写不出
   195 词成人新闻改写。阈值调多少都救不了，**需要教研拍板是否放宽到 `A1–A2`（1721 词族）**。

**验证工具**：`tools/verify_vocab_reflow.py` —— **三轮对照**实验，别只跑两轮。

```
R1 无回灌（算出规避词） → R2 带回灌（处理组） → R3 无回灌（对照组）
R1↔R3 差值 = 噪声基线；只有证据 > 噪声才敢说「回灌有效」
```

**🔴 为什么必须带对照**：LLM 随机性足以淹没单次对比。实测踩过 ——
B2 档第 1 轮就达标、**根本没收到任何回灌**，第 2 轮照样从 0.8% 涨到 2.1%。
**单次「改前 vs 改后」分不清是改动生效还是碰巧。**
同理，统计「是否改善」时**只评价真正收到回灌的档**，未处理的档不参与。

另一个更锐利的判据是**词级依从率**：第 1 轮要求规避的词，在第 2 轮文章里还剩几个
（`_stem_variants` 双侧降词干比对）。实测 65–78%，不被整体波动稀释。

⚠️ 它同时踩过两个入参坑：`summary`（500）与 `avoid_words`（原 500，已改 4000）
都有 **max_length 硬上限** —— 素材正文要放 `facts_text`，否则工作流 0.5 秒秒退。

**背景**：Bryan 反馈「文章内容没问题，但语言不够 natural / 不像 native」。
**结论：不是模型问题，是提示词** —— 同素材同模型（`deepseek-v4-pro`）四档实测，
**B2+ 明显最自然、A1-/A2 最生硬**，而约束强度恰好也是「B2+ 最松、低档最紧」。

**A1-/A2 曾有四条「反自然」约束**（拆掉前每一条都在制造翻译腔）：

| 约束 | 后果 |
|---|---|
| 「禁用习语/隐喻」 | 地道搭配全禁 → 只剩主谓宾直陈句 |
| 「实词重复鼓励」 | `good family help` 一句里说两遍 |

#### 改低档提示词时最容易踩的三条

1. **禁掉一种表达手段，必须同时给替代手段** —— 只写「禁止用 `X means Y` 凑段」，
   实测 A2 当场掉到 190 词（下限 240）。必须补「要解释就用具体例子句」+「这不等于可以少写」。
2. **压篇幅的约束天然会压句数** —— 补完篇幅后 A1- 又变成「每段只写 1 句」、句长冲到 12.7（规格 7–9）。
   凡涉篇幅的改动，**词数 / 句数 / 段数三个指标要一起看**。
3. **机械判据别依赖「正文有没有换行」** —— 自然度检查 v1 假定正文按 `\n\n` 分段，

   这类**全篇级误报**。改为**按句子切分 + 只看相邻句对**，对分段方式不敏感。
   ⇒ 写完检查逻辑**必须在本地用真实输入复现一遍**，别只看「它报了个 warn」。

- B1 组蓝思/句长仍会冲高（实测 B1.2 20.0 词/句、估算 1097L），是既有波动。

## 四档字数与每段词数（2026-09-21 现行 · 改提示词前必看）

**所有数字必须成对改** —— 现行关系是「全文区间 ≈ 12 × 每段词数」。只改一侧会出现**物理不可达**的区间。

| 档 | 靶心 | 硬区间（±15%） | 每段词数 | 每段句数 | 平均句长 |
|---|---|---|---|---|---|
| A1- | 150 | **128–172** | 11–14 | **1–2**（不要求每段 2 句） | **6–9** |
| A2 | 240 | **204–276** | 20–22 | 2（强制） | 10–13 |
| B1 | 380 | **323–437** | 28–35 | **2 句为主** | 14–17 |
| B2+ | 550 | **468–632** | 41–50 | **2 句为主** | 18–24 |

- **区间 = 靶心 ±15%**，不是拍脑袋：实测模型对字数的控制精度就是 ±15% 左右，给 ±5%（10 词宽）会持续 fail。
- **A1- 的数学下限是 168**（每段 2 句 × 句长下限 7 × 12 段）。要压到 150，必须**同时放宽句数与句长**
  （每段 1–2 句 + 句长 7→6）—— 这是 2026-09-21 Bryan 明确授权的例外，其余标准不动。
- **A2 的下限 240 是数学下限**：每段 2 句 × 每句最少 10 词 × 12 段。
- **B1 / B2+ 一律「2 句为主」**：写「2–3 句」模型就取 3 句（B2+ 取 3 句会把上限锁死在 12×2×24 = 576）。

### 🔴 六轮实测：模型对字数的控制只有 ±15%，别指望「改数字就到位」

同一素材、只改提示词，六轮实测（靶心 150 / 240 / 380 / 550；✓ = 落在区间内）：

| 档 | 基线 | R1 只改数字 | R2 词数优先 | R3 低句数为主 | R4 算式 | R5 放宽句数+句长 | R6 加「2 句为主」 |
|---|---|---|---|---|---|---|---|
| A1- | 185 | 185 | 186 | **129 ✓** | 198 | **169 ✓** | 187 |
| A2 | 267 | **275 ✓** | **241 ✓** | **236 ✓** | **234 ✓** | **237 ✓** | 202 |
| B1 | 453 | 455 | **415 ✓** | **385 ✓** | 442 | 442 | **346 ✓** |
| B2+ | 742 | **601 ✓** | **614 ✓** | 455 | **503 ✓** | **556 ✓** | **562 ✓** |

**三条硬结论**：
1. **模型是按「每段句数 × 句长」铺段的，不是按「全文字数」**，而且句数**默认取区间上限**
   （写「每段 2–3 句」它就写 3 句）。⇒ **想控字数，先控句数** —— 把「2 句为主」直接写进【篇幅】。
2. **模型不肯写单句段落**：用三种措辞逼它（「多数段 1 句」/「1 句为主」/「全篇约 18 句」），
   六轮里只有一轮被逼到 129，其余都回到 185–198。⇒ A1- 实际长期落在 **170–198** 一带。
3. **单次运行的达标率约 60–70%**（六轮：A1- 2/6 · A2 5/6 · B1 3/6 · B2+ 5/6）。
   **要稳定达标只能靠「不达标自动重跑该档」，纯调提示词已到极限。**

**改动面是 4 处，缺一不可**（`tools/patch_word_count.py`，幂等 + 37 项回读核验）：
GEN 4 个生成节点的**规格块 + 自查块**（同一数字各出现 2–3 次）· GEN `nodeValidate` 的
`[词数下限, 上限, 蓝思下限, 上限, 句长下限, 上限]` · FACT `nodeGrade` 的 4 档速查表 ·
前端 `SPECS`（`len` 中英各 4 处 + A1- 的 `avg`）。

⚠️ `nodeValidate` **通常只改词数两个数**；A1- 句长改动时才动第 5 个数（7→6）。

🔴 **幂等铁律：所有替换必须「锚点 → 最终文案」一步到位。**
任何「A→B 再由 B→C」的链条，第二次跑时 A 项的 `new` 已被 B 项消费 → `new in txt` 判定失效
→ `count(old)=0` → 抛错（已在 A2 句长与 A1- 句数上各踩一次）。
**验证手法：连跑三次比 `sha256`** —— 比看日志数「跳过几项」可靠得多（日志会骗人，sha 不会）。

### 🔴 最关键的一条（历史成因，理解设计必读）：**四档都是 12 段，所以「段数不一致」这个唯一机械信号会失效**

### 🔴 新坑 A：`事实一致性` 在高档会**误判 fail** —— 模型把数字写成英文单词

`GEN_VALIDATE_CODE` 用事实卡里的**阿拉伯数字**做子串匹配：

```js
factNums = (JSON.stringify(JSON.parse(factcard||'{}')).match(/\d[\d,.]*%?/g)||[]).slice(0,6);
const missNums = factNums.filter(n => !String(article||'').includes(n));
if (factNums.length && missNums.length === factNums.length) → fail('事实卡关键数字未出现')
```

**实测**：B2+ 三档全判 fail，但正文其实**完整覆盖了事实**——只是写成了
`two hundred trees` / `five degrees Celsius`，而事实卡里是 `200`。
子串匹配找不到 `"200"` → 全缺 → fail。B1 组因为写了 `200` 反而侥幸通过。

⇒ **看到高档 `事实一致性` fail，先做"英文数词 vs 阿拉伯数字"归一化再判定**，
不要直接当成生成质量问题报给教研。修法：校验器侧加数词归一化（推荐），或生成侧强制阿拉伯数字。

## 知识库语料替换（这版 Dify 没有「文档级文本更新」API）

## 标准操作流程

```
1) GET draft 拿 hash + 当前图（**先落盘存证**，第 3.5 步要用）
2) 改图生成器 → 重建 JSON
   - FACT / GEN：改各自生成器
   - MAIN：**不要手改**，改完 FACT/GEN 后跑 `tools/build_main_graph.py` 重新拼装
   - ⚠️ 同一文件的多处改动**串行**做，改完回读核验（并行 Edit 会静默丢改动）
3) 跑静态校验器：变量可达性 + start 可达性 + 输出变量存在性 + 无环
   （并用对照实验确认校验器有效）
3.5) **diff 线上 draft vs 本地新图** —— 差异必须**恰好等于本次改动**，多一处就停手排查
   （防止本地快照过期，把已上线的修复整段回退）
4) dify_push_graph.mjs 推送 draft（带 hash）—— **FACT / GEN / MAIN 三个 app 都要推**：
   FACT `12e8c26d-cbcc-43c2-94bb-20926226cb3d`、GEN `f4462032-2919-49e0-b123-bb5160c96c28`、
   MAIN `466e1815-c5bb-4d50-8437-2fc4768dd4f0`
5) dify_run_draft.mjs 试跑，看逐节点耗时/状态/输出
   （不满意就回 2，draft 反复试不影响线上）
6) dify_publish.mjs 发布
7) 用 service API 走 **streaming** 做线上端到端冒烟
   或直接 `tools/dify_run_app.py --app=main --inputs='{"material":"..."}'`
8) 清理：Dify 侧确认 workflow-runs 里有你刚发起的记录
```

> ⚠️ **发布顺序**：FACT / GEN / MAIN 要**连续发布**，避免出现
> 「12 档分级 + 3 档生成」或「MAIN 还是旧三档」的中间态。

### 🔴 铁律 1：**「必须逐字不变」的动作不能交给模型**（2026-09-22 真跑抓到）

不精简 = 保留原文。原设计靠提示词让模型「逐字原样输出」并写明「你的角色只是一台复制机」——
**真跑仍被改写**：`has moved from a hobby` → `has grown from a small hobby into`（443 vs 原文 454 词）。

解法：**新增 `nodeFinal`（code）硬取 `nodeStart.material`**，模型在该分支只输出占位符
`__KEEP_ORIGINAL__`（有占位符/空输出一律回落原文，绝不产出空正文）。
顺带把耗时从 14.1s 压到 **10.6s**（少了一次长输出）。

> 泛化：**提示词只适合"生成"，不适合"搬运"**。凡结果必须精确等于某值，用 code 节点取。

### 🔴 铁律 2：导入母稿时，**每段词数是分段的唯一依据**（2026-09-22 二次重写）

> 上一版把「每段词数」整个删掉了，理由是「保留原文时词数不由我们控制」——**这个判断是错的**。
> 切开一段不改一个字，只是把切分点从段末移到句末，词数完全可控。
> 后果（Bryan 用真实 B1 母稿验收时抓到）：319 词、8 个自然段（54/45/34/38/44/47/39/18），
> 模型**原样照搬**，6 段越界。而全文本来完全合格 —— **问题只在切分点**。

**Bryan 拍板的口径**：

| 项 | 值 |
|---|---|
| 每段目标 | 母稿档位规格：B1 **28–35** / B2+ **41–50** |
| 合格带 | **±5 词** → B1 **23–40** / B2+ **36–55** |
| 段数 | 「全文词数 ÷ 每段目标」自然算出；**10–15 段内不提示** |
| 全文字数 | **不参与分段决策** |
| 切分点 | 句末优先、**均匀优先**，可据大意微调 |

依据（原话）：段落是 **APP 上的阅读卡片**，「不能太长也不能太短」。
⇒ 「能合则合、尽量靠近 12 段」在母稿场景**废弃**。

**段数判定**：跑出 **<10 或 >15** 段时回 `seg_note`（前端黄条 + 「仍然继续生成」，**不阻断**）。
另有非阻断信号 `fallback`：勾了精简却没拿到稿子 → 已回落原文，**必须显式提示**。

🔴 **段数区间 2026-09-22 由 8–15 收窄为 10–15**，因为下界 8 已不成立：
B1 硬区间 323–437 ÷ 每段 28–35 ⇒ 最少要 10 段才够字数（8 段 × 35 = 280 < 323）。

#### 精简模式的口径（2026-09-22 Bryan 拍板，**取代「定死 12 段」**）

| 项 | 值 |
|---|---|
| **硬指标** | **全文字数落进该档硬区间**（B1 **323–437** / B2 **468–632**） |
| 段数 | **按内容大意自然分**，不固定；**10–15 段 = 兜底判定区间** |
| 越界 | 跑出 10–15 才算 `segBad`，**且绝不静默**（warn 必须写依据） |

数学依据：B1 323 ÷ 28 ≈ 11.5、B2 468 ÷ 41 ≈ 11.4 ⇒ **真正宽松的落点是 11–13 段**，
10 段时 B1 每段须 ≥32.3 词、B2 须 ≥46.8 词，余量很窄。

三处配套改动（缺一即失效）：
- `SIMPLIFY_SYS`：条数从「固定 12 条」改为**按字数反推**（B1/B2 都要 **10–15 条**）；
  并明说「**少于 10 条一定欠字数，这是硬伤**」。
- `SIMPLIFY2_SYS`：段数 = 上一步清单条数（10–15），**一段写一条、不合并不拆分**；
  自查项①改「段数 = 清单条数吗？且落在 10–15 内？」，③改「**B2 必须落 468–632；B1 必须落 323–437**」。
- `SEGMENT_SYS` 模式 B：**直接采用上一步的既有切分**，不重新合并拆分；
  唯一例外是某段明显超上限（B1 超 45 / B2 超 65 词）才在句末切一刀，切完超 15 段再把相邻短段合回去。

⚠️ 旧版分段提示词有三条**互相打架**的约束（每段词数 + 「段数 = 总词数 ÷ 每段词数」+ 上限 16 段）：**已删。**

### 🔴 铁律 3：模型切不准时，**代码兜底**（`nodeClean` 里的 DP 质检）—— **分模式**

模型按指令切分的稳定性只有六七成。`nodeClean`（code 节点）解析后跑质检：

1. 找出仍越界的段 → 候选窗口 **自身 / 左邻 / 左二 / 右邻 / 右二**
2. 每个窗口用 **DP** 重切：`k = round(词数 ÷ 合格带中点)`，最小化「各段偏离中点」平方和 + 越界罚
3. **只在窗口总越界量下降时**采纳

四条要点（都是踩出来的）：

- **判据必须是「总越界量」而不是「有没有越界」** —— B1 一段 44 词（超 4）比切成 30+14（14 严重偏短）更好。
- **窗口必须到 ±2** —— 27+18 两段单独治不好（切完还是 27/18），拉上更外一层才腾得出空间。
- **切不动要报出来**（「一整句话 60 词」句末无处可切）→ `out_of_band` + warn，不许静默。
  ⚠️ 只在**保留原文**模式报 —— 精简稿跑的是段数兜底而非长度重排，拿 ±5 带算越界会误导。
- 🔴 **质检必须分模式走**（2026-09-22 修）：
  - **保留原文** ⇒ `segs` 按 ±5 合格带**重排**（原逻辑）。
  - **精简稿** ⇒ **只调段数、不按长度重排** —— 重排会切坏大意边界，把「一段讲一件事」搞烂。
    实现：`const SEG_LO = 10, SEG_HI = 15;`，>15 就每次合并**相邻词数之和最小**的一对，
    <10 就拆最长的段（`dpSplit`），两侧各最多 40 轮，`autoFixed++` 计数。

> ⚠️ 曾经的「**精简模式不质检**」（契约=正好 12 段，补切一刀变 18 段）**已作废** ——
> 段数不再定死 12，兜底逻辑改为**把段数拉回 10–15**。

用户要求**静默**（界面不标哪几段被调过），所以 `auto_fixed` 只作内部计数。
