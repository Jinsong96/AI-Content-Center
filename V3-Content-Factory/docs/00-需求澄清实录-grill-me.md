# 00 · 需求澄清实录（grill-me 深度追问）

> 日期：2026-09-28 · 参与：Bryan（需求方/产品经理）+ AI（追问方）
> 本文是**过程记录**：每一轮问了什么、答了什么、由此锁定了什么。

## 1. 追问的起点

**任务**：为「AI 内容生产平台」做一次完整的需求澄清，产出可执行的规格。
**工具**：`grill-me` 技能 —— 不做发散脑暴，而是就一条决策链反复追问到没有歧义为止。

**一开始就被圈定的边界（Bryan 主动划的）**：

- 不谈绩效、KPI、组织汇报口径。原话：「你先不要管那些乱七八糟的」。
- 只聚焦一件事：**做一个可验证的 demo**，且能被后端接手实现。
- 验收方三方各点一遍：**领导 + 本人 + 同事**。
- 验收标准只有两条：**① 能不能跑出内容；② 内容是否符合要求。**

### 触发这次澄清的现状（本轮最重要的输入）

> V1 版本搭了 **8 个工作流** + 大量提示词，产出内容**不如**：① 教研老师 skill 蒸馏出的 skill；② 裸 Claude；③ WorkBuddy + DeepSeek。

即：**半个月做的平台，效果不如直接把内容喂给大模型。** 这是必须解决的起点问题。

## 2. 追问链条（按轮次）

### R1 · 为什么 V1 更差？→ 诊断

**AI 的诊断（Bryan 认可）**：8 个工作流串联 = **8 次信息损耗 + 0 次质量增益**。
每一步都是纯 AI 翻译，中间没有真人判断、没有外部数据、没有老师方法论注入 → 只累积误差，不累积质量。
而强模型一次调用吃全部上下文、零损耗 → 更好是必然。

**结论：V1 骨架对、内核装错。**
- 可留：前端页面 / bridge 转发层 / 接口 / 部署链路
- 该丢：8 个工作流的提示词（跟强模型正面拼质量，拼不赢）

**由此确立 demo 的证明目标**：从「展示我的编排」改为**「展示裸模型给不了的增量」**。

### R2 · 增量到底在哪？A 稳 / B 批量 / C 门槛低 / D 可管控

**Bryan 拍板**：
- **主证 = A（稳）+ C（门槛低）**
- 加分 = B（批量快）+ D（可管控）

理由（AI 提，Bryan 认）：质量翻倍无法当场证明；**稳定与低门槛是领导能当场点一遍验证的维度**。

### R3 · 「稳」和「门槛」靠什么落地？

**关键发现**：把老师工具包 zip 拆开看，它比 V1 强的根本原因**不是提示词更好，而是它自带 evals**。

`build_cards.py` 里的 `check()` 是一个**确定性质检器**，14 类校验：
卡片数对齐 · 词数占比区间 · 单句最长词数 · 主题词必须出现 · 题目数/选项数/答案字母有效 ·
解析与题干引用的英文**必须逐字存在于本级正文**（防幻觉）。

→ 输出 `✓ 通过` / `需修改 N 处`，**这就是「可验证」的落地**。

**对照 V1**：8 个工作流、**0 个确定性质检器**，全靠 AI 自评。
→ **V1 缺的不是模式，是 evals。**

**A + C 的落点**：
- 稳 = **确定性质检器**（不靠模型更聪明，靠脚本挡掉不合格）
- 门槛 = **前端把 skill 变成按钮**（老师不写 prompt、不装环境）

### R4 · 「符合要求」指形式还是内容？

**Bryan 答**：**内容质量第一位**，且他指的实质是**跨级别一致性**。三条新信息：

1. 最终交付对象是终端用户，用户会读 A1/A2/B1/B2 的文章，改写不得让用户读不懂大意。
2. **主题词不能因为低级别语料里没有就丢掉**（例：`honesty` 是主题词，A1/A2 也必须保留）。
3. **自适应阅读机制**（此前未知，重要）：用户读文章时难度**动态调节** ——
   读 A1 这段觉得容易 → 下一段换 A2 → 还容易 → 下一段 B1；觉得难则反向降。
   **即用户读的是「同一篇文章、逐段混搭难度」的连续文本。**

**推论**：自适应把「四级卡片语义对齐」从加分项变成**硬需求** —— 用户从 A1 第 1 段接着读 A2 第 2 段，必须接得上。
→ 新增改写约束：**降级不能删掉「承上启下」的信息**，否则跨级降读会断裂（后定为 `bridge_broken`）。

### R5 · 模型怎么配？要不要多 agent？

**Bryan 的方案**：至少两个模型 —— **生成用 GPT 系，检查用 DeepSeek 系**，两个模型交替检查。
**多 agent**：具体问题具体分析，没想法，AI 认为有必要就加。

**AI 的判断（Bryan 认可）**：
- 方向对（异源模型交叉检查，避开同源偏差），但三点修正：
  ① **不是所有检查都该用模型** —— 词数/句长/引用逐字一致这类规则能判的必须用脚本；模型只该管「需要判断」的事。
  ② **检查方要用推理更强的模型**，不是随便另一个模型。
  ③ **成本控制：脚本先筛，只把可疑项交给模型。**
- **正确用法是分层**：L1 形式 = 脚本（全自动）；L2 一致性/保真 = 异源模型裁判（半自动）；L3 可用性 = 人工抽检。
- **不需要 agent 框架** —— 「生成模型 + 检查模型」本身就是 Multi-agent 的最小形态（角色分离），两次 API 调用即可。

### R6 · 唯一标准是什么？平台的定位是什么？

**① 唯一标准 = 教研老师工具包。** 原话：「之前知识库里的所有内容（关于剧场、词汇、语法等）一切先不要，就按照教研老师的工具包来。」
→ V1 仓库里除老师这条线以外的内容**全部搁置**，不作为 demo 参照。

**② 定位 = 内容工厂**（Bryan 明确纠正了 AI 的理解）：
- 平台产出物 = **四个不同难度的文章 + 一套题目**
- 下游 = **专门的后台管理系统**（把文章导入、再做其他工作）→ 上线到 **APP**
- 原话：「我们现在这个定位是内容工厂。」

### R7 · 阅读器算不算平台的一部分？

这里出现过一次张力：Bryan 先说过「做平台不做 APP，多一个阅读器没有问题」，后说「定位是内容工厂」。
**Bryan 最终确认**：**阅读器保留，且不能只读 —— 要可编辑。** 自适应难度调节**留到下一期**。
→ 阅读编辑器定位为**审校窗口**（存在目的是证明产出物真能读、内容真满足要求），不是面向终端用户的阅读产品。

**「一份题目」= 四个级别各 3 道题，合起来算一套**（已确认）。

### R8 · A1- 的人名怎么处理？（老师工具包内部冲突）

**冲突**：项目说明要求「A1- 全文最多 3 个专有名词」，但老师示例实际把 `Benjamin Franklin` → `A man`、
`Philip Graves` → `A scientist`；而 A2/B1 保留人名 → **用户从 B1 降到 A1-，必然接不上**。

**Bryan 的裁决**：
> **关键人名、地名、关键信息必须保留，不受「≤3 个」限制。**
> 可以说 `Graves, a scientist`（**保留名字 + 同位语说明身份**），
> 不能把 Franklin 写成 `A man`、Graves 写成 `A scientist`。

→ 这条**可以机械化检查**（A1- 必须含原文人名）→ 成为脚本**第 15 类**规则。
→ 老师示例本身违反此规则，需更新范例或显式写例外。

### R9 · 老师手改之后要不要自动重跑质检？

**Bryan 答**：**需要重跑，但不自动 —— 给按钮让用户手动点。**

**AI 的补充修正**：重跑分两级 ——
- **L1 脚本质检**（毫秒、免费）= 按钮随便点
- **L2 模型裁判**（贵、慢）= 单独按钮、人决定
- **「自动循环到通过」只用在生成阶段，不用于人手改之后。**
  （理由：老师手改的往往是内容层问题，形式质检照样全绿 → 「循环点按钮到通过」是空转。）

### R10 · 有两条输入链路（此前未知）

- **模式 1（有原文）**：原文等级**由人工判定好、系统不质疑**；给 B2+ 原文 → 只往下生成 B1/A2/A1-，
  **不重新输出原文**（B2+ 就是原文本身，只切卡 + 出题）。
- **模式 2（无原文，只有事实卡）**：如热点搜集来的素材 → 直接生成四个难度。
  → **本期不做**，只预留接口位置。

### R11 · 词表给不给？判据写不写？

**词表**：Bryan 决定**先不给**，让模型自己判断有没有特别难的词。理由（AI 附议并写进提示词）：
① 词表是累计列表，判不了「这个词在语境里能否被猜出」；② **词表会跟硬要求打架** ——
主题词（`honesty`）本身可能偏难但必须保留，给词表 → 判成超纲 → 触发重写改掉主题词；③ 整体复杂度已被脚本管住。

**判据**：Bryan 质疑「判据不好定，定太死或太松都会出问题，**反而可能把第一模型生成的好内容判坏**」，
建议**先不加细判据跑一遍看效果**。

**AI 的回应（被采纳）**：
- 「没有判据」在物理上不存在 —— 提示词总要写东西。真正可选的是**粒度**：
  A 档（只给任务）/ B 档（类名 + 例子）/ C 档（边界细则 + P0/P1）。**停在 B 或退到 A**。
- 必须分开「判据」与「知识」：判据（口径）可以不给，**知识（各级语法/难度预期）必须喂**。
- **「判坏了」的真正来源不是判据，是「裁判误报 → 自动重写」这条链** →
  第一版**把裁判与重写解耦**：裁判只标记 → 给人看 → 人点「重写这张」。
- **目标导向而非规则导向**：给「为什么」（读者是谁、会跨级连续读、要保住什么），不给「什么算错」。

→ 产出 `03-裁判提示词-v0-无判据版.md`。

### R12 · 交付形态与工程约定

**Bryan 拍板**：
- **必须新建干净项目，代号 V3**，与 V1/V2 完全区分开
- 模型 A = **GPT 系**；模型 B = **DeepSeek 系推理模型**
- 存储 = **JSON 落盘**（沿用老师 `articles/{id}/` 目录结构）
- 部署：Railway 可用（实测首页 2.4–3.2s，够用；不建议 serverless —— 1–4 分钟任务会超时）
- **自动修复要自动触发**：原话「只要不达标就自动去做，尽可能自动化，**人只发挥最关键的作用**」

### R13 · 界面反馈（实现之后）

- 第一轮原话：「整体颜色用浅色系，注意整体的美感和搭配，可以用简约大气的极简风格，你目前还是可以的，**主要是颜色**。还有整体的适配，这个我在浏览器中打开太小了。」
- 第二轮原话：「背景色可以换成浅色吗，就是像 WorkBuddy 一样，**有浅色和黑色的切换**。然后**增加一个英文版本**，在右上角可以切换中英文的版本。」
- 第三轮（本文撰写时）：改名 **「一鹿知 · 内容生产平台」**；去掉顶栏那个与页面内重复的「新建生产」按钮。

## 4. 已锁定的需求（施工依据）

### 4.1 定位与产出

- **定位**：内容工厂（不是 APP）。产物交给下游后台管理系统 → 上线 APP。
- **产出物**：四个难度文章（B2+ / B1 / A2 / A1-）+ 一套题目（**每级 3 题，共 12 题**）+ 质检报告。
- **输入**：
  - 模式 1（本期）：一篇英文原文（等级人工已定）→ **只向下生成 B1/A2/A1- 三级**；
    **B2+ = 原文本身，不重新生成**，只切卡 + 出题。
  - 模式 2（下期）：事实卡（无原文）→ 四级全生成。

### 4.2 两个核心质量要求（最高优先级）

1. **四级文章内容大意保持一致**
2. **语言难度符合对应等级**（词汇 + 语法不超纲）

**受众映射（Bryan 明确）**：

| 级别 | 对应学段 |
|---|---|
| A1- | 小学生 |
| A2 | 初中生 |
| B1 | 高中生 |
| B2+ | 高中生以上 |

### 4.3 三条硬约束（不可违反）

1. **主题词不得因降级而丢失**（`honesty` 这类主题词在 A1/A2 也必须保留）。
2. **A1- 关键人名、地名必须保留**，不受「≤3 个专有名词」限制；
   可写 `Graves, a scientist`（原名 + 同位语说明身份），**不可泛化成 `A scientist`**。
3. **跨级降读必须接得上** —— 降级不得删掉「承上启下」的信息（`bridge_broken`）。

### 4.4 质量保障机制

- **两层关卡**：L1 确定性脚本（形式）+ L2 异源模型裁判（语义）。脚本在前，模型在后。
- **只两次模型调用**（生成 1 次 + 裁判 1 次），其余全是确定性代码。
- **自动修复**：脚本错误自动修（≤3 轮）；裁判 P0 自动修（≤2 轮）；**P1 只标记、交人工**；超轮次 → `needs_human`。
- **L1 / L2 重跑按钮分开**：L1 免费随便点，L2 花钱人决定。
- 裁判 v0 = **无细判据版**，且**与重写解耦**（只标记不改稿）。

### 4.5 人机分工

> 机器能判的一律自动；**口径问题不替人拍板**。
> 人只做三件事：① 判断原文等级 ② 看质检报告 ③ 拍板 P1 和 `needs_human` 的项。

### 4.6 交互形态

- 单页 Web（工作台 / 编辑台 / 质检面板 / 导出）
- **浅色系极简风**，支持**浅/深主题切换**
- **中英双语**，右上角切换
- 阅读器**可编辑**（审校窗口，非终端用户阅读产品）
- 品牌名：**一鹿知 · 内容生产平台**
