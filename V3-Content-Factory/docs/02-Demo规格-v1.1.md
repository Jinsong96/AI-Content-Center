# 分级阅读内容工厂 · Demo 规格 v1.1

> 目的：一份能跟后端对接的可验证 demo 规格。
> 原则：唯一业务标准 = 教研老师的《分级卡片工具包》；范围之外的一切（自适应难度调节、发布、多维知识库）都不做。
> 日期：2026-09-28 · v1.1 已定 5 项决策，并新增「自动修复循环」

---

## 0. 一句话定义

**输入一篇英文原文（B2+），产出一套可直接使用的分级阅读材料：**

> 四个难度的文章（A1- / A2 / B1 / B2+）＋ 每个难度 3 道题（共一套 12 道）＋ 质检报告
> → 可在平台上**阅读、编辑**，可**导出 docx**。

平台 = **内容工厂**（项目代号 **V3**）。下游（专门的后台管理系统 + APP）负责把成品导入、再处理、上线。

**已定决策**

| 项 | 结论 |
|---|---|
| 模型 A（生成） | **GPT 系** |
| 模型 B（裁判） | **DeepSeek 系推理模型** |
| 存储 | **JSON 落盘** |
| 自动修复 | **自动触发，不达标就修**，人只在机器修不动时介入 |
| 项目 | **新建干净项目 V3**，与 V1（内容生产后台）、V2（分级卡片页）完全隔离 |

## 1. 验收标准（这是「可验证」的定义）

**谁来验**：领导、项目负责人、同事，三方各自独立跑一遍。

| 编号 | 可验证项 | 判据 |
|---|---|---|
| V1 | **能出内容** | 粘贴一篇英文原文，能在界面上拿到四个难度的成稿 |
| V2 | **形式达标** | 质检报告显示 `通过`（14 类校验 0 错误） |
| V3 | **内容达标** | 语义裁判报告无 P0 问题；抽检 3 张卡，四级讲的确实是同一件事 |
| V4 | **门槛低** | 操作者不写提示词、不装环境、不看代码，只用界面 |
| V5 | **可编辑** | 任何一张卡、任何一道题都能就地改，改完能重跑质检 |
| V6 | **可交付** | 能导出与老师模板一致的 docx |

> **V2 是硬门槛**：这一步不通过，后面不用看。

## 2. 生产链路

### 主干（2 次模型调用）

```
英文原文 B2+
   │
   ├─① 生成 ──── 模型 A · GPT 系（一次调用，输出完整 JSON）
   │
   ├─② 校验 ──── 确定性脚本（14 类规则，老师的 build_cards.py）
   │
   ├─③ 裁判 ──── 模型 B · DeepSeek 系推理模型（只判对错、不改内容）
   │
   ├─④ 渲染 ──── 确定性脚本（JSON → docx）
   │
   └─⑤ 阅读 · 编辑 ── 平台界面（四级切换 + 就地编辑）
```

### 自动修复循环（关键机制）

**只要不达标就自动修，直到达标或到上限；上限到了才交给人。**

```
① 生成
   ↓
② 脚本质检 ──有错──→ 局部重写（只重写报错的那张卡 / 那道题）──┐
   │                    ↑                                    │
   │0 错                └────────────── 最多 3 轮 ←───────────┘
   ↓
③ 语义裁判 ──有 P0──→ 局部重写相关卡 → 回 ② → 最多 2 轮
   │
   │无 P0
   ↓
④ 渲染 → ⑤ 完成

若超出轮次仍有错 → 停止，标记 `needs_human`，把问题清单（定位到卡/句）交给编辑
```

**三条设计理由**

1. **必须有轮次上限。** 无上限会死循环并持续烧 token。取 3 轮（形式）+ 2 轮（语义）是成本与效果的折中，可配。
2. **只做局部重写，不整篇重跑。** 脚本和裁判都会定位到具体卡片，只重出那一张 —— 这是老师原设计「重写 B1 / 修改 A2 Q2」的用法，也是最省 token 的做法。
3. **兜底交给人。** 「人只发挥最关键的作用」= 机器修不动的时候人来看。这也是 `needs_human` 这个状态存在的意义。

> 机制依据：这属于「带外部反馈的反思」——反馈来自确定性脚本而非模型自评，可靠性高得多。

### 其它设计要点

1. **生成只有一次调用，绝不串联。** 多步串联只累积失真、不累积质量。
2. **能机械验证的一律用脚本，不交给模型**（数词、句长、引用是否逐字存在）。
3. **脚本在前、模型在后**：脚本挡形式，模型挡语义；脚本先筛，只把可疑项交给模型，省 token。
4. **裁判用异源模型**，避免同源偏差（同一模型倾向认为自己写得对）。
5. **裁判只判错、不改稿**。

## 3. 页面清单

| 页面 | 职责 | 关键交互 |
|---|---|---|
| **P1 生产台** | 提交原文、启动生产、看进度 | 粘贴/上传原文 → 「开始生产」→ 步骤条（生成 / 校验 / 自动修复 / 裁判）；显示当前第几轮修复 |
| **P2 阅读编辑器** | 读 + 改四个难度的文章与题目 | 难度切换（A1-/A2/B1/B2+）；卡片就地编辑；题目编辑；「重写这张卡」 |
| **P3 质检面板** | 展示 14 类校验 + 语义裁判结果 | 问题定位到「级别 + 第 N 张卡 + 原句」；点击跳转；「重跑校验」；`needs_human` 高亮 |
| **P4 导出** | 生成 docx | 「导出 docx」→ 下载 |

> P3 可以做成 P2 的右侧栏/抽屉，不必独立页面。

## 4. 接口清单（给后端）

> 约定：`article_id` 为文章唯一标识；所有返回为 JSON；错误沿用 HTTP 状态码 + `{ error: { code, message } }`。

### 生产

| # | 接口 | 入参 | 出参 | 说明 |
|---|---|---|---|---|
| 1 | `POST /api/articles` | `{ original_text, title_hint?, auto_fix?: { enabled: bool, max_check_rounds: 3, max_judge_rounds: 2 }, run_judge?: bool }` | `{ article_id, job_id }` | 默认 `auto_fix.enabled = true`、`run_judge = true` |
| 2 | `GET /api/jobs/{job_id}` | — | `{ status, step, round, progress, error? }` | 轮询。`status`: `pending / generating / checking / auto_fixing / judging / done / needs_human / failed` |

> **异步 + 轮询**是推荐做法（一次生产含自动修复约 1–4 分钟）。若 demo 求简，可用同步阻塞 + loading，但接口形态要保持可替换。

### 读取

| # | 接口 | 入参 | 出参 | 说明 |
|---|---|---|---|---|
| 3 | `GET /api/articles` | `?page` | `{ items: [{ id, title_en, title_zh, status, created_at }] }` | 工作台历史列表 |
| 4 | `GET /api/articles/{id}` | — | 完整 Article 对象（见 §6） | 编辑器主数据源 |

### 编辑

| # | 接口 | 入参 | 出参 | 说明 |
|---|---|---|---|---|
| 5 | `PUT /api/articles/{id}/cards` | `{ level, index, text }` | `{ ok: true }` | 保存某张卡的编辑 |
| 6 | `PUT /api/articles/{id}/questions` | `{ level, index, q?, options?, answer?, explanation? }` | `{ ok: true }` | 保存某道题的编辑 |
| 7 | `POST /api/articles/{id}/rewrite` | `{ level, index, instruction? }` | `{ text }` | **人工触发的局部重写**（调模型 A）；自动修复走的是同一条内部逻辑 |

### 质检

| # | 接口 | 入参 | 出参 | 说明 |
|---|---|---|---|---|
| 8 | `POST /api/articles/{id}/check` | — | `{ stats: [], errors: [], warnings: [], passed: bool }` | 重跑 14 类脚本校验 |
| 9 | `POST /api/articles/{id}/judge` | — | `{ issues: [] }` | 重跑语义裁判（模型 B） |

### 导出

| # | 接口 | 入参 | 出参 | 说明 |
|---|---|---|---|---|
| 10 | `POST /api/articles/{id}/export` | — | `{ download_url }` | 用 `template.docx` 渲染 |

## 5. 两次模型调用的契约（核心）

### 调用 1 — 生成（模型 A = GPT 系）

| 项 | 内容 |
|---|---|
| 系统提示词 | **直接复用**老师《项目说明_粘贴到Project指令》全文，不改 |
| 用户输入 | 英文原文（B2+） |
| 输出 | 严格 JSON，结构见 §6（老师已定义，不改） |
| 失败处理 | JSON 解析失败 → 原样重试 1 次；仍失败 → 报 `status: failed` |
| 关键约束 | **一次调用出全部四个级别 + 全部题目**，不允许拆成多次 |
| 复用场景 | 自动修复与人工「重写这张卡」都复用它，只是改为「只输出这一张卡的 JSON 片段」 |

### 调用 2 — 语义裁判（模型 B = DeepSeek 系推理模型）

| 项 | 内容 |
|---|---|
| 系统提示词 | **需新写（暂缺）** —— 老师工具包只有生成、没有裁判 |
| 用户输入 | 原文 ＋ 按卡对齐的四级卡片（第 N 张卡的 A1-/A2/B1/B2+ 四个版本为一组） |
| 输出 | `{ issues: [{ card_index, type, severity, evidence, detail }] }` |
| 只判不改 | 不返回改后的正文，只返回问题与依据 |

**`type` 枚举（8 类 · 已按「不与脚本重复」精简）**

| # | type | 含义 | 严重度 | 谁能查 |
|---|---|---|---|---|
| 1 | `fact_added` | 低级别新增了原文没有的事实 | P0 | 仅裁判 |
| 2 | `fact_dropped` | 核心事实被删除 | P0 | 仅裁判 |
| 3 | `fact_altered` | 主体 / 立场 / 事实被改变 | P0 | 仅裁判 |
| 4 | `card_misaligned` | 第 N 张卡在各级讲的不是同一件事 | P0 | 仅裁判 |
| 5 | `bridge_broken` | **承上启下信息被删，跨级降读时断裂**（新增约束，老师版没有） | P1 | 仅裁判 |
| 6 | `topic_word_weak` | 主题词出现了，但语境不足以推断词义 | P1 | 仅裁判 |
| 7 | `answer_unsupported` | 答案在本级正文里找不到依据 | P0 | 仅裁判（脚本只查引文逐字存在，不查「能否支撑答案」） |
| 8 | `option_unfair` | 干扰项不合理（无出处 / 与正确答案同义） | P1 | 仅裁判 |

> 原草案里的第 9 类 `topic_word_missing`（主题词缺失）**已删除** —— 脚本第 4 条已经硬性拦截，
> 裁判再查一次没有增量，只增加 token。
>
> **这是 demo 唯一需要新增的提示词工程**，也是本期最大的不确定项。

## 6. 数据模型

```
Article {
  id, title_en, title_zh, topic_words[],
  original_text,
  b2_card_starts[],

  levels: {
    "A1-": { cards: [string], questions: [{ q, options[4], answer, explanation }] },
    "A2":  { cards: [...], questions: [...] },
    "B1":  { cards: [...], questions: [...] },
    "B2+": { questions: [...] }        // B2+ 正文由原文按 b2_card_starts 切出，不重新生成
  },

  check_report: { stats[], errors[], warnings[], passed },
  judge_report: { issues[] } | null,
  fix_log: [ { round, scope, target, before, after } ],   // 自动修复留痕，便于追因

  status, created_at, updated_at
}
```

**存储：JSON 落盘**（已定）。建议 `data/articles/{id}.json` 每篇一个文件 + 一个 `index.json` 存列表。
好处：零依赖、可直接肉眼查看、备份就是复制目录；后续换数据库时迁移路径也清晰。

## 9. 部署建议（含实测数据）

**实测（本机在境内，2026-09-28）**

| 站点 | 首页耗时 |
|---|---|
| Railway（V1 现用） | **2.4 – 3.2 s** |
| GitHub（海外基准） | 0.76 s |
| 百度（国内基准） | 0.09 – 0.12 s |

> 注：本机连接时间接近 0，可能走了代理，该数据**偏向乐观**；真实国内用户体验可能更慢。

**判断**

- **Railway 够用，可以先上。** 理由：V1 已验证可部署、零学习成本；而真正耗时的是生成（1–4 分钟），
  首屏 2–3 秒不是瓶颈。
- **风险**：国内网络抖动可能影响长时间轮询；若领导对速度敏感，换 **腾讯云轻量应用服务器**（国内节点，
  约 ¥60–100/月），代价是要自己运维（装 Python、配 nginx、域名备案）。
- **不建议** serverless（Vercel / 阿里云函数计算等）：生成任务 1–4 分钟，会触发超时限制。
- **只剩你自己演示时**：本机跑 + Cloudflare Tunnel 穿透，零成本且改代码即时生效。

**结论：demo 阶段用 Railway；等形态定下来、要正式给多人用，再迁腾讯云轻量。**
