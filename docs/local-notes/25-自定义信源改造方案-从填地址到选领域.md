# 25 · 自定义信源改造方案：从「填地址」到「选领域」

日期：2026-09-14
状态：**方案（待 Bryan 拍板，未动工）**
前置：`docs/24-自定义信源可行性实测与冷启动告警对齐.md`（实测矩阵与 5 处交付缺口）

## 0. 需求复述 → 设计原则

Bryan 的 4 条约束，逐条翻译成硬约束：

| 原话 | 推导出的硬约束 |
|---|---|
| 「必须是真实能跑的，不能有半点马虎或糊弄，老师用不了就是我的问题，会扣绩效」 | 每条链路**本地 + 线上双验证**；**0 处假数据**（随机数、硬编码热度一律清除）；失败必须可见、可解释 |
| 「需要跟后端对接，真实工程化，原型要真实跑通」 | 信源必须是**后端可配置的真实数据**，不是前端写死；接口要有 limit / 去重 / 错误回传 |
| 「用户是教研/市场老师，没有技术能力，分辨不了什么是 RSS」 | 界面上**不出现** `RSS` / `feed` / `Atom` / `URL 格式` 等技术概念 |
| 「所有设计必须围绕用户的需求和习惯」 | **默认成功**（打开就能用，不需配置）；失败时**必须给下一步**，不能只报错 |

### 一句话方案

> 把「让老师填一个源地址」改成「让老师选一个领域」。
> 平台预先维护一张**经过双端验收的信源目录**（数据，不是代码）；
> 「贴链接」作为第二条路径保留，自动识别类型，成功后可保存为「我的订阅」。

### 配套的设计铁律（贯穿全文）

1. **选源的责任在平台，不在老师。** 老师只表达"我要体育的"，平台负责"体育用哪些源、哪些源活着"。
2. **失败路径与成功路径同等重要。** 老师遇到失败会直接卡住并来找 Bryan。所以失败必须给出「原因 + 现在能用什么」。
3. **看不见的技术，才是不需要理解的技术。** 界面上凡是出现非业务词汇，都是设计失败。

## 1. 为什么必须这样改（三条实测事实，来自 docs/24）

**事实 ①：老师随手能复制的链接，现在基本只产出一句网页标题。**

| 老师会贴的 | 现状产出 |
|---|---|
| 虎扑首页 / 步行街 | 降级 1 条（只有页面标题） |
| 懂球帝首页 | 降级 1 条 |
| 澎湃 / 人民网 / ChinaDaily 首页 | 降级 1 条 |
| 喜马拉雅专辑页 / Apple Podcasts 页 | 降级 1 条 |

**事实 ②：真正能出内容的是 RSS 直链，而老师不可能知道那个地址。**

播客 RSS 直链 2975 条、ESPN RSS 38 条、BBC Sport RSS 77 条、人民网 RSS 100 条 ——
但地址形态是 `https://www.people.com.cn/rss/politics.xml`，这是**开发者才知道的地址**。

**事实 ③：即使贴对了地址，现在也点不动（代码级硬伤）。**

`state.hot = HOTS.length + i` → 下标越界 → `pickHot()` 读 `HOTS[i]` 得 `undefined` → 直接 `return`。
自定义源**没有接入真实热点的选中通道**（`pickRealHot`）。

**结论**：这三条叠加的结果是 —— 把「域名」丢给老师，等于把「选源」的责任丢给老师，而老师没有这个能力。
平台必须自己维护「哪些源可靠、怎么抓」。

## 2. 产品形态：三个入口

### 入口 A · 领域频道（主路径，覆盖 ~80% 场景）

老师打开「定制热点」，看到的**不是输入框，是一面卡片墙**：

```
┌─────────┬─────────┬─────────┬─────────┐
│  ⚽ 体育  │  💻 科技  │ 🤖 AI·教育│ 📈 商业  │
├─────────┼─────────┼─────────┼─────────┤
│  🌍 国际  │  🎓 教育  │  🩺 健康  │  🎨 文化  │
└─────────┴─────────┴─────────┴─────────┘
```

点「体育」→ 直接出 10–20 条**真实热点**（来自该领域挂载的多个源）→ 点选 → 进入与主热点榜**完全一致**的生成流程。

**关键点**：
- 零配置。老师不需要知道源是什么。
- 条数由 `limit` 控制（后端默认 20），不会出现 2975 张卡片。
- 每条带：中文标题 / 来源媒体名 / 时间 / 原文链接。
- 「热度」只显示**真实信号**（几个源在报同一件事 → 来源数；或发布时间新鲜度），**不再有随机数**。

### 入口 B · 贴链接（辅助路径，"我有想看的网站"）

保留粘贴框，但**性质变了**：从"配置信源"变成"临时添加一个源"。

```
[ 粘贴任意链接 ………………………… ]  →  [ 获取内容 ]

系统自动判断，三种结局：
  ✅ 识别到订阅源（播客/RSS）  → 直接用，质量最高
  ✅ 识别到新闻/垂直站列表页   → 抽出 10–20 条真标题
  ✅ 需要桥接层的平台（如 YouTube）→ 走桥接，或明确告知
  ❌ 抓不到                    → 说明原因 + 直接推荐同类可用源
```

**成功后可点「保存到我的订阅」**，下次一键使用。
这一步把「一次性高级操作」变成「一次操作，长期可用」，正好解决"老师不懂技术但想用特定站"的矛盾。

### 入口 C · 我的订阅（保存过的领域与源）

只需**勾选/取消**，以及重新命名。不暴露任何技术参数。

### 失败路径的设计（这一条要单独说）

老师遇到失败会卡住，所以**失败页必须回答三个问题**：

1. **发生了什么** —— "虎扑的内容需要用浏览器打开，我们的服务器取不到"
2. **现在能怎么办** —— 直接给出该领域的可用源（如「懂球帝 29 条 / ESPN 38 条」），一键切换
3. **要不要留着** —— 允许保留这个源，后续适配后再启用

> 反面教材（现状）：`未从这些信源抓到内容（源可能被墙或非 RSS），已用演示数据`
> —— 这句话同时犯了三个错：含糊（"可能被墙"）、甩术语（"非 RSS"）、**用演示数据掩盖失败**。

## 3. 后端工程化清单

### 3.1 信源目录（新增 `backend/sources_catalog.json`）

**这是整个方案的地基。** 每个领域的可用源以**数据**形式维护，加源/换源不改代码。

```jsonc
{
  "domains": [
    {
      "id": "sports", "name": "体育", "icon": "⚽",
      "sources": [
        { "id": "dongqiudi", "name": "懂球帝", "kind": "list",
          "url": "https://www.dongqiudi.com/", "verified_local": true, "verified_live": true },
        { "id": "espn", "name": "ESPN", "kind": "rss",
          "url": "https://www.espn.com/espn/rss/news", "verified_local": true, "verified_live": true }
      ]
    }
  ]
}
```

字段说明：
- `kind`：`rss`（直链） / `list`（列表页抽取） / `bridge`（需桥接层）
- `verified_local` / `verified_live`：**只有两个都为 true 的源才允许进目录**（血泪教训见 §6）

### 3.2 列表页抽取器（新增，把已验证原型工程化）

上一轮在 `/tmp` 里验证过的启发式（同域 `<a>` + 锚文本 12–80 字 + 排除导航词），
实测产出：ChinaDaily 99 / 懂球帝 29 / 人民网 12 / 澎湃 9。

需要工程化的点：
- 排除词表要可配置（登录/注册/下载/客户端/广告/招聘…）
- 返回**标题 + 绝对 URL + 来源域名**（现状只返回一句 `<title>`）
- 假阳性过滤：JS 渲染站（虎扑步行街 49 条全是版块名）要能识别出来并**判定为失败**，而不是当成 49 条真内容

### 3.3 统一抓取接口（改造 `/api/scan`）

| 项 | 现状 | 改为 |
|---|---|---|
| 条数上限 | **无**（播客 RSS 2975 条全出） | `limit` 参数，默认 20 |
| 去重 | 无 | 按 URL + 标题去重 |
| 排序 | 无 | 按时间倒序（有 `date` 时） |
| 字段完整性 | 丢 `url` / `summary` / `fulltext` | 三个字段必须回传 |
| 源名称 | 只传 `urls`，用户填的名字丢失 | 传 `urls` + `names`（或 JSON），保留用户命名 |
| 热度 | `heat=60` 硬编码 | **删除**；改真实信号（来源数 / 新鲜度）或直接不显示 |

### 3.4 健康度与自愈

- 每次抓取记录每个源的成败 → 复用已有 `/api/source-health`
- 连续失败 N 次（建议 3）自动降级为「暂停」，并在后台日志留痕
- 管理侧可见"哪个源挂了多久"，这是运营能维护的前提

### 3.5 禁止清单（面向"不能糊弄"）

- ❌ `Math.random()` 造的假热度（`runCustomScan()` 兜底分支里现有一处）
- ❌ 硬编码 `heat=60` / `srcs=1`
- ❌ 抓不到时用"演示数据"填充
- ❌ 静默降级（失败必须回传 `errors` 让界面能说清）

| 阶段 | 内容 | 做完后用户能做什么 |

## 6. 验收标准（"真实能跑"的可执行定义）

**铁律：任何源都必须本地 + 线上各测一次。**
反例：澎湃首页**本地能抓、线上 403**；头条**本地要 Chrome、线上却能通**。只看一边必然误判。

| 验收项 | 判据 |
|---|---|
| 领域频道 | 至少 3 个领域，每个领域 ≥8 条**真标题**（不得来自"网页标题"降级） |
| 点击链路 | 任意一条能选入并进入生成流程（端到端跑通一次） |
| 假数据 | grep 全站：`Math.random` 与自定义源 `heat=60` 均为 0 处 |
| 失败路径 | 抓不到的源：有明确原因 + 有可用替代源 |
| 回归 | 主热点榜 / 生成流程 / 审核页不受影响 |
| 线上 | 部署后首批次 `errors=0`，且与本地结果逐条一致 |

## 7. 能力边界（必须提前讲清，避免老师踩坑）

| 类型 | 支持 | 说明 |
|---|---|---|
| RSS / 播客直链 | ✅ 最好 | 标题 + 摘要 + 链接 + 时间 |
| 新闻 / 垂直站列表页 | ✅ 好 | 10–99 条真标题 |
| YouTube 频道 | ⚠️ 需桥接 | 机房 IP 直连原生 feed 返回 404；rss-bridge 公共实例实测可通（15 条），但公共实例不可靠，生产需自建 |
| 虎扑等 JS 重站 | ❌ | 线上无浏览器，取不到内容 |
| 微信公众号 | ❌ | 无公开接口 |

**边界的产品化处理**：对 ❌ 类型，界面上不出现"失败"，而是**根本不列为可选**，
或者在老师贴入时明确告知并给出替代 —— 而不是让老师看到一个错误码。

## 附：本轮结论速览

- 现有「自定义信源」**不能真实运转**，但不是抓取能力的问题 —— 是**交付链路断了**（点不中）+ **输入形态错了**（要求老师懂 RSS）。
- 方案核心：**平台维护信源目录（配置化）+ 老师只选领域 + 贴链接作为辅助且可保存**。
- 最大风险不是技术，是**失败体验**：老师一旦卡住就来找 Bryan。所以失败路径必须给原因和替代方案。
