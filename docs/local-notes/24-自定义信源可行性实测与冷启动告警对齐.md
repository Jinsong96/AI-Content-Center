## 1. 顺手改的那 3 行：翻译缓存冷启动不再告警

### 问题回顾
部署重建容器后，「首批次」调用 `/api/trends` 会出现一条 warn：

```
[warn] cache.translation.load: /app/backend/.toutiao_en_cache.json 不存在
```

`_is_real_degradation()` 对任何非渲染类错误都返回 True → API 回 `degraded=true` → 前端弹
「部分信源未抓到，结果可能少于实际」。而事实上 **0 个源失败**。该批次结束文件写回，第 2 次调用即自愈。

### 根因
同一文件里两个缓存加载函数行为不一致：

| 函数 | 文件不存在时 |
|---|---|
| `_load_tag_cache()`（内容标签缓存） | `return {}` —— 并明确注释「冷启动属正常情况，不该每次都告警」 |
| `_load_tr_cache()`（翻译缓存） | 直接进 `except` → 记 warn |

### 改动（`backend/agent_reach_bridge.py`，1 处原子替换，命中数 1）
在 `_load_tr_cache()` 的 `try` 之前加文件存在性前置判断，与 `_load_tag_cache()` 对齐：

```python
def _load_tr_cache():
    if not os.path.exists(_TR_CACHE_FILE):
        # 冷启动（含 Railway 部署重建容器、缓存文件随旧容器一起没了）属正常情况，
        # 不该每次都告警 —— 否则部署后首批次会记一条 warn，把界面误挂上
        # 「部分信源未抓到」横幅（实际 0 个源失败）。对齐 _load_tag_cache() 的行为。
        return {}
    try:
        ...
    except Exception as e:
        # 文件存在但读不动（损坏 / 权限），有兜底 → warn 级，这种情况才值得报警
        note_error("cache.translation.load", e, severity="warn", file=_TR_CACHE_FILE)
        return {}
```

### 验收（本地，逐条）
| 场景 | 期望 | 实测 |
|---|---|---|
| 缓存文件不存在（冷启动） | 不告警，返回 `{}` | ✓ ERROR_LOG 0 条 |
| 缓存文件存在但 JSON 损坏 | **仍告警**（可观测性不能被改坏） | ✓ `cache.translation.load` 照常记 warn |
| 对照 `_load_tag_cache()` 冷启动 | 0 条 | ✓ 0 条 |

线上：commit `b0175e04383e`，远端 sha `503b718937c5`。

## 2. 自定义信源：能不能真实运转？

### 2.1 现有链路（读代码确认）
```
前端 s1() 表单（name / type / url）
  → state.user.sources[]（会话内存，未持久化）
  → runCustomScan() → fetchRealScan()
  → GET /api/scan?urls=<所有源用逗号拼接>
  → 后端 fetch_scan(urls)：逐源
       ① fetch(url) → parse_feed()  ← 仅认 RSS 2.0 <item> / Atom <entry>
       ② 失败 → discover_rss(html) ← 找 <link rel="alternate" ... rss/atom/feed>
            → 发现则抓该 feed → parse_feed()
       ③ 仍失败 → 兜底：只取网页 <title>，标记 _degraded
  → 前端写入 state.customHots[]（独立于主热点榜）
```
`parse_feed()` 要求条目**同时**有 `title` 和 `link`。

### 2.3 YouTube 的 404 是什么原因（已查证 + 实测）
- 从**频道页**能反向确认 `channel_id` 完全正确：线上抓 `@TEDEd` 时，后端 `discover_rss()`
  从页面里读出的 feed URL 是 `...?channel_id=UCsooa4yRKGN_zEE8iknghZA`——和我手工构造的**一模一样**。
- 但直接请求该 feed → **404**。这是**已知的、结构性问题**：YouTube 对**机房 IP**（Vercel / AWS / Railway 这类）
  的 `feeds/videos.xml` 请求返回 404/500，同一 URL 从浏览器或普通主机访问正常；2025-12 起还出现过间歇性大规模 404。
- **替代端点实测（均从 Railway 发起）**：

| 端点 | 结果 |
|---|---|
| YouTube 原生 feed | 失败 404 |
| openrss.org（by channel_id / by handle） | 失败 404 |
| piped.video/feed/<id> | 降级（不是 feed） |
| rsshub.app 公共实例 | 失败 403（限流） |
| **rss-bridge 公共实例** | **OK-RSS，15 条** ✅ |

→ **YouTube 信源可以打通**，但必须走「桥接」层，不能直连原生 feed。
（15 条是 YouTube 单频道 feed 的硬上限。）

### 2.4 「新闻列表页」这条路的上限（本地实测抽取能力）
用通用启发式（同域 `<a>` + 锚文本 12–80 字）从首页抽文章候选：

| 站点 | 页面体积 | 可抽候选 | 样例 |
|---|---|---|---|
| ChinaDaily 首页 | 119 KB | **99 条** | “Xi: China, India can achieve shared growth” |
| 虎扑·步行街 | 301 KB | 49 条 | 全是版块名+发帖数（**假阳性**，页面 JS 渲染） |
| 懂球帝 | 328 KB | **29 条** | “中国男篮7人得分上双105-61菲律宾…” ← 体育场景 |
| 人民网 首页 | 133 KB | **12 条** | “走进尼雷尔领导力学院 ｜ 一带一路·第一现场” |
| 澎湃 首页 | 61 KB | **9 条** | “国家卫健委：正在起草托育服务法…” |
| 虎扑 首页 | 487 KB | 1 条 | 只有备案号（JS 渲染） |

另外：`people.com.cn/rss/politics.xml` → **100 条**；`xinhuanet.com/english/rss/worldrss.xml` → **20 条**。
→ 只要**喂对 feed 地址**，人民网/新华网质量极高；但用户不会知道要去哪找 feed 地址。

### 2.5 结论：三条路各自的天花板

| 路 | 用户输入形态 | 现状 | 天花板 |
|---|---|---|---|
| **A. RSS/Atom 直链** | `https://…/feed.xml` | ✅ 已能用 | 质量最高（标题+摘要+链接+时间），但**用户不会知道这个地址**；且无条数上限（实测 2975 条） |
| **B. 新闻/垂直站列表页** | `https://www.hupu.com/` | ⚠️ 只拿到一句网页标题 | **可救**：改成「列表页抽取」后，澎湃 9 / 人民网 12 / 懂球帝 29 / ChinaDaily 99 条。**JS 重度渲染站（虎扑）仍救不了**（线上无浏览器） |
| **C. 播客 / YouTube 平台页** | `https://youtube.com/@TEDEd`、Apple Podcasts 链接 | ❌ 只拿到网页标题 | 播客：需从平台页解析出 feed（部分平台可，Apple 页可解析出 feed id）；YouTube：需加桥接层（rss-bridge 已验证可通）。两者都是**平台专用适配**，不能靠通用启发式 |

**「还是最好是新闻网页版的网站形式？」** —— 实测答案：**是的，新闻/垂直站的列表页最值得做**（B 路），
因为①用户贴的就是首页这种随手可得的地址；②抽取质量已被证明（12–99 条真标题）；
③不依赖任何第三方桥接服务，稳定性可控。
但 B 路**不能替代** A 路和 C 路：RSS 直链质量最高应继续支持；播客/YouTube 是用户明确提的场景，
需要各自的适配器，属于「按需逐个加」而非「一次通用解决」。

## 3. 代码层面查出的交付缺口（本轮未动，仅记录）

### 3.1 前端：自定义信源条目**无法作为素材使用**（最严重）
- 卡片点击 `d.onclick = () => { state.hot = HOTS.length + i; render(); };`
- 但 `curHot()` 是 `return (… && HOTS[state.hot]) ? HOTS[state.hot] : null;`
- `state.hot` 被设成越界下标 → `curHot()` 返回 `null`（或上一次选中的 `state.realHot`）
→ **点自定义信源卡片，选不中、进不了生成流程**。真实热点用的是 `pickRealHot(h)`，自定义卡片没有对应入口。

### 3.2 前端：扫描结果在映射时丢字段
`runCustomScan()` 里 `real.map(r => ({ custom:true, type:"url", name: r.source, tag:{zh:"真实抓取",…}, topic: r.topic, cn: r.source, heat: r.heat||60, srcs:1 }))`
丢掉：
- `url` → **点不进原文**
- `summary` → 看不到摘要
- 用户自己填的**领域标签** → 被硬编码成「真实抓取」
- 且 `hasUsableText()` 要求正文 ≥200 字才放行，而自定义条目根本没有 `fulltext`
→ 即便选得中，也会被「请粘贴原文」拦截。

### 3.3 后端：自定义条目没有真实热度
`fetch_scan()` 里 `g["heat"] = 60`、`g["srcs"] = 1` 硬编码 → 界面上的「热度 60」和「信源 1」是**假数据**。
真正的热点榜有聚类与热度排序，自定义源这条完全没有。

### 3.4 无条数上限
播客 RSS 直链实测返回 **2975 条**，前端 `state.customHots` 全量渲染 → 2975 张卡片。
`/api/scan` 也没有 `limit` 参数。

### 3.5 源名称未回传
`/api/scan?urls=` 只传 URL，不传用户填的名称 → 后端用 `host_of(u)` 当源名，
前端再拿 `r.source` 当 `name`。**用户填的「虎扑体育」这类名称在链路上丢了**。

## 4. 建议方案（待 Bryan 拍板）

### 第 1 步：让自定义信源「能用起来」（不改抓取能力，先补交付链路）
1. **列表页抽取兜底**：`fetch_scan()` 的第 ③ 步从「只取 `<title>`」升级为「抽同域文章候选（标题+链接）」，
   取前 N 条（建议 10–20），并把 `_degraded` 语义改为「列表页模式」。
   → 直接救活 澎湃/人民网/ChinaDaily/懂球帝 这类站。
2. **补 `limit`**：`/api/scan?urls=&limit=20`，前端也传；防 2975 条淹 UI。
3. **前端补交付**：自定义条目走与真实热点同一套选中入口（复用 `pickRealHot`）、
   带上 `url`/`summary`/用户标签、去掉假的 heat/srcs（显示「自定义源」而非伪热度）。
4. **源名称回传**：`/api/scan` 改成 `urls` + `names`（或传 JSON），保留用户命名。

做完这 4 条，用户贴「澎湃首页」「懂球帝首页」就能得到 **10–20 条真标题的定制热点**，且能点进去用。

### 第 2 步（按需）：平台适配器
- **YouTube**：频道页 → 已验证能解析出 `channel_id`（后端 `discover_rss` 已经读到了），
  但原生 feed 对机房 IP 404 → 需接 rss-bridge / 自建 RSSHub。
  ⚠️ 公共实例不可靠（rsshub.app 已 403），生产要么自建要么换源。
- **播客**：RSS 直链已可用；平台页需逐个适配（Apple 页可解析 feed id，喜马拉雅/小宇宙需另做）。
- **虎扑**：JS 重度渲染且反爬强，线上无浏览器 → **建议明确不支持**，在 UI 上给出提示而非静默降级。

### 第 3 步：把「降级」说清楚
当前用户看到「未从这些信源抓到内容（源可能被墙或非 RSS），已用演示数据」——
但真实原因可能是「该站需要 JS 渲染」「该站对机房 IP 返回 403」「这是视频型事件」。
建议按 `_degraded` 的具体类型分型给出可行动提示（如「该站需浏览器渲染，请改用 RSS 地址」）。
