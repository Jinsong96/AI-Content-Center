## 🔴 关键踩坑：骨架块必须带【逐段篇幅】

第一版只拼了【段落骨架】，结果（真模型 e2e 第 1 条链路）：

```
段数 A1=11 A2=11 / 骨架 11 段 → ✅ 对齐
A1- 逐段 [20,14,19,25,27,30,26,27,28,25,23]  ← 规格 11–14，只 1/11 落带
```

**段数对齐了，但每段写成 20–30 词** —— 模型默认按「压缩但不减段」处理，
不告诉它每段该多长，它就不会压到位。

补上一行后（`PER` 取自前端 `LIC_PER_PARA`，与图 B `nodeValidate` 同源）：

```
【逐段篇幅】A1- 每段 11–14 词；A2 每段 20–22 词。按段分别控制，不卡全文字数。
→ A1- 11/11 落带、A2 11/11 落带
```

⚠️ 这行**不是改图 C 的提示词**，是输入侧喂料（Bryan 拍板的「约束进输入」）。
两个探针里都**逐字复制**了这段拼装逻辑，改前端必须同步改，否则探针就失去意义。

## 已知缺口（没做，别当成做完了）

1. **大意一致仍无代码闸门** —— 段数由代码硬校验，但「第 i 段讲第 i 段的事」是语义，
   现行做法是**事后用事实检查图核对**（4/4 pass），**不是生成时的闸门**。
   要补的话：把 `nodeSemCheck` 那套判据搬进 lite 链路，或把事实检查图接进回炉。
2. **保留清单仍未做** —— 实测清单不成体系反而有害（只保护主题词+专名时 A1- 保真度 90% → 81%）。
3. **母稿 >525 词**时 B1 档每段 28–35 词会算出 15 段以上；现锁上限 15、放宽每段词数。
4. **渠道波动**（同图耗时 92 倍波动 / 偶发非法 JSON / 502）：生成侧已 3 次上限，
   图 A 侧仍是单次调用（失败会给红条 + 「重新切分」重试路径，未做自动重试）。
