# 27 · 定制热点：需求重定义与功能边界

日期：2026-09-14
视角：产品（需求层，不涉及实现）
取代：`docs/26`（用户画像与场景写偏了）
依据：`backend/agent_reach_bridge.py`（FEEDS / CN_FEEDS / CONTENT_TAGS）+ `frontend/index.html` 代码核实

> **已修正两次前提，这是终版**：
> ① 不是"外部老师" → 是**公司内部同事**；
> ② **不是备课工具** → 是**内容生产后台**，产出全部供给**阅读 APP**。

---

## 1. 前提：这个后台到底在干什么

| 项 | 内容 |
|---|---|
| 产品 | AI 英语分级阅读 **内容生产后台** |
| 产出流向 | 文章库 → **阅读 APP**（C 端读者）+ **自有版权文章** |
| 生产链路 | `素材创建（含热点搜集）→ 素材库 → 文章生产 → 文章库 → APP` |
| 主力用户 | **教研老师** —— 内容生产 + 素材选取 |
| 辅助用户 | **市场 / 运营老师** —— 配合素材热点选取 |
| 素材来源 | ① 热点（时效）② 自有版权 / 公版书 ③ **定制信源（本次要做的）** |

**关键认知**：老师的 KPI 是**给 APP 稳定供给内容**，不是给自己备课。
所以驱动不是"我下周讲什么"，而是"**内容库需要什么、还缺什么**"。

内容需求坐标 = **6 大类 × 81 个内容标签 × 12 个子档**（代码：`CONTENT_TAGS`）
（世界 10 / 科学 14 / 文化 17 / 商业 13 / 成长 17 / 故事 10）

---

## 2. 核心判断：这个功能解决「覆盖度」，不是「时效性」

| | 主热点榜（已有） | 定制信源（本次） |
|---|---|---|
| 回答的问题 | **时效性**：今天发生了什么 | **覆盖度**：库里缺的主题，素材从哪来 |
| 素材性质 | 热点素材（保鲜期 2 周） | **主题素材**（常青，可长期供给） |
| 内容标签 | 撞上哪类算哪类 | 按 6 大类 81 标签**定向补齐** |
| 选源责任 | 平台 | 平台预设 + 老师补充 |

### 2.1 硬数据（代码核实，不是推测）

固定信源只有 **18 条**：

- 英文 `FEEDS`（13 条）：CGTN×5、NPR、Global News、The Verge、ScienceDaily、Science News、Live Science、Variety、Billboard
- 中文 `CN_FEEDS`（5 条）：人民网·文化/时政/国际、新华网·时政

而它们的 `themes` 字段只出现三类：**`world` / `culture` / `science`**。
（`fetch_trends()` 里 `rss_targets = [... if theme in themes]` —— 主题不在列表里，该源**根本不会被请求**。）

**结论：一半主题没有信源。**

| 大类 | 标签数 | 有固定信源吗 |
|---|---|---|
| 世界 world | 10 | ✅ |
| 科学 science | 14 | ✅ |
| 文化 culture | 17 | ✅ |
| **商业 business** | **13** | ❌ **零信源** |
| **成长 growth** | **17** | ❌ **零信源** |
| **故事 story** | **10** | ❌ **零信源**（故事类目前靠自有版权 / 公版书入口） |

→ **40 / 81 个标签、约 49% 的主题，没有任何固定信源。**
（注：`CGTN · Business` 这条源被标成 `world`，所以连名字带 business 的源都没喂到商业类。）

### 2.2 因此，结论要改

> 定制信源**不是"锦上添花的个性化功能"，而是补半个主题盲区的供给通道**。
> 它的成功标准不是"能抓到一个 RSS"，而是——
> **让 6 大类主题都有可预期、可复用的素材来源。**

这也解释了为什么老师会提这个需求：不是想玩新功能，是**内容库有缺口、现有信源供不上**。

## 3. 用户需求清单（细颗粒度）

| # | 场景 | 老师会说的话 | 真实需求 | 现状 |
|---|---|---|---|---|
| 1 | **主题缺口补货**（教研，最高频） | 「库里'成长'类太少了，该生产几篇」 | 按**主题**找到可用素材 | ❌ 固定源无 growth / business / story |
| 2 | 热点时效补货（教研） | 「这件事很热，APP 上该有一篇」 | 时效性素材 | ✅ 主热点榜已覆盖 |
| 3 | 我信得过的源（教研） | 「Edutopia / TED-Ed / BBC Learning English 适合我们读者」 | 把本领域好源接进来，**稳定供给** | ⚠️ 能填，但刷新即丢（§7.2） |
| 4 | 素材要能直接用（教研） | 「只有标题我没法生成」 | **有正文 / 能打开原文** | ❌ 链接被丢，点不进去（§7.3） |
| 5 | 政策与行业情报（市场 / 运营） | 「教育部新政策」「竞品在做什么」 | 权威 + 可引用 | ⚠️ 无专门入口（也落在 business 盲区） |

| 7 | 别让我重配（共性） | 「配一次就该记住」 | **持久化** | ❌ 假承诺（§7.2） |

## 4. 需求 → 承接

| 需求 | 由谁承接 |
|---|---|
| 1 | **F1 主题频道**（主路径，零配置） |
| 2 | 主热点榜（已有，不动） |
| 3、7 | **F2 我的信源** + **F3 我的订阅** |

> **关键取舍**：「选主题」放主路径、「贴链接」放辅路径。

## 5. 功能定义

### F1 主题频道（P0，主路径）
- **做什么**：按平台既有 6 大类组织，每个主题 = 一组已验证信源；老师点一下，扫出该主题的候选素材。
- **老师动作**：点一个卡片。**就这一步。**
- **命名对齐平台词表**（世界 / 科学 / 文化 / 商业 / 成长 / 故事）——不新造词汇，降低认知成本。
- **首批只上有实测数据的**（§8）；**商业 / 成长 / 故事这三个盲区要新补源**——这正是本功能的核心价值，但工作量也在这一步。
- **验收**：点「成长」→ 出来 ≥8 条带标题、能点开原文的候选；能一键加入素材库并进入生产链路；全流程不出现任何技术词。

### F2 我的信源（P1，辅路径）
- **做什么**：粘贴链接 → 后端判定类型 → 入库 → 参与扫描。
- **老师动作**：**只粘贴**。删掉现在的「网址 / YouTube / 其他」下拉——这是平台该做的判断。
- **判定结果必须说人话**（F2 的核心不是抓取，是让人看懂）：

| 判定 | 界面文案 |
|---|---|
| 找到订阅源 | 「可直接使用」 |
| 只能抽列表页 | 「可用（取到 N 条标题）」 |
| 视频 / 音频页 | 「只能取到话题线索，需自行准备原文」 |
| JS 渲染 / 反爬 | 「该站抓不到，建议换一个来源」 |
| 需登录 | 「该内容需要登录，暂不支持」 |

### F3 我的订阅（P2）
- F2 的持久化 + 一键复用 + 删除。
- ⚠️ **后端现在没有存的地方**，这是新增能力，不是改前端。

### F4 失败可见（P0，横切）
- 每个源的成功 / 失败 / 降级原因回显；**删除所有假数据兜底**。
- **验收**：0 条结果时，界面必须能回答「哪个源失败了、为什么、我该换什么」。

## 6. 边界：明确不做什么

| 不做 | 理由（**有实测 / 代码支撑**） |
|---|---|
| **不承担"库存缺口决策"** | 文章库已有"库存图归类 / 冷却比对 / 槽位匹配"的标签机制，但**缺口没有可视化**。"现在该生产什么主题"是上游问题；本功能只负责「主题定了之后，素材从哪来」，不负责决定生产什么。**别把它当补货调度器做。** |
| **不做 RSS 阅读器** | 老师要的是素材，不是订阅管理；做了会把后台拖成资讯客户端 |
| **不承诺任意网站** | 虎扑等 JS 重度渲染站线上无浏览器：抽 49 条全是假阳性，实际只拿 1 条 |
| **不承诺 YouTube 稳定** | 机房 IP 请求原生 feed **实测 404**；只有桥接实例能通，公共实例已 403 限流 |
| **不承诺播客 / 视频给正文** | 音视频产出只能到「话题线索」级，正文需另找或用字幕转写（另立项） |
| **不支持需登录内容** | 微信公众号 / 付费墙拿不到，与其静默失败不如明确排除 |
| **不设无限量** | 播客 RSS 直链**实测 2975 条**，必须设上限（建议 20 条 / 源） |
| **不暴露技术词** | 界面不出现 RSS / feed / 抓取频率 |
| **不替代主热点榜** | 两者分工不同（§2），不要合并 |

## 7. 现状与需求的 5 个冲突（都必须修）

### 7.1 假数据兜底 —— 最严重
`index.html:3372-3383`：抓不到内容时用 `Math.random()` 造热度（55–93）、造条数（1–4）、
造标题（「本周热度上升」）。
→ **老师分辨不了真假。** 直接违反「不能糊弄」，是这条功能里最该先删的东西。

### 7.2 「信源保留」是假的
UI 文案：「同一同事再次登录，信源保留」。
实际：`SOURCE_STORE` 是内存对象，**刷新即丢**，回到预置值。
→ 要么实现持久化，要么改文案。**不能留假承诺。**

### 7.3 交付丢字段：产出用不了
`runCustomScan()` 映射时丢了 `url`（→ 点不进原文）、`summary`、老师填的领域标签
（被硬编码成「真实抓取」），且 `cn` 写成**源名**而不是标题。
→ 卡片上显示的是域名。**这就是「能不能真正用」的直接答案：现在不能。**

### 7.4 假热度
`fetch_scan()` 里 `heat=60`、`srcs=1` 硬编码 → 「热度 60 · 信源 1」是无意义的假指标。

### 7.5 无条数上限
2975 条会全量渲染成 2975 张卡片；`/api/scan` 也没有 `limit` 参数。

## 8. 能力天花板（边界从哪来，全部来自实测）

| 路 | 老师输入的形态 | 现状 | 上限 |
|---|---|---|---|
| **A · 订阅直链** | `…/feed.xml` | ✅ 可用 | 质量最高（标题+摘要+链接+时间），但**老师不知道去哪找这个地址** |
| **B · 新闻/垂媒首页** | `thepaper.cn`、`dongqiudi.com` | ⚠️ 只拿到一句网页标题 | **最值得做**：列表页抽取后，澎湃 9 / 人民网 12 / 懂球帝 29 / ChinaDaily 99 条真标题；JS 站（虎扑）仍救不了 |
| **C · 播客 / YouTube** | `youtube.com/@TEDEd` | ❌ 只拿到网页标题 | 播客需解析平台页；YouTube 必须走桥接层——**逐个适配，不能一次通用解决** |

**已有实测数据、可直接落地的主题**：体育（BBC Sport 77 条 / 懂球帝 29 条）、
世界（CGTN + 人民网 + 新华网）、科学（ScienceDaily 等）、文化（Variety / Billboard / 人民网·文化）。

**必须新补源的三个盲区**：商业、成长、故事。→ **建议先各找 3–5 个候选源做实测，再定能不能上。**

## 9. 优先级

| 级别 | 内容 | 判据 |
|---|---|---|
| **P0** | F4 删假数据 + 交付链路修复（能点进去用）+ F1 主题频道（先上有源的主题） | 不修等于没有；风险最低、可立刻端到端验证 |
| **P1** | **补商业 / 成长 / 故事的源** + F2 添加我的来源 | 这两个是"覆盖度"的命门；只做 F2 不补源，盲区还在 |
| **P2** | F3 持久化（含后端存储） | 依赖 F2，且是新增能力 |
| **P3** | §6 边界清单 | 明确拒绝，防范围蔓延 |

## 11. 验证方式（内部用户的优势：可直接测）

不用问卷。**请 1 位教研老师 + 1 位市场老师各操作一次现有界面**，重点看两件事：

- **她是先点主题、还是先看今天热搜？** → 决定「覆盖度 vs 时效性」谁是主路径，也就决定 F1 的优先级。
- **她会不会主动说"库里缺 XX"？** → 若有，说明 §2 的判断成立，且 §6 那条边界（不承担库存缺口决策）需要再讨论。

若观察结果与本文不符，**以观察为准**，功能边界重裁。
