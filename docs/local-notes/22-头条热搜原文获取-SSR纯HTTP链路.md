# 22 · 今日头条热搜原文获取：SSR 纯 HTTP 链路

> 起因：Bryan 报「今日头条热搜无原文」。给的关键线索是——点进原文链接，「事件详情」
> 这几个字下面会有一个标题，标题是个超链接，导向正文。
> 结论：**对的**，而且这条线索直接指向了正确解法。全链路不需要 Chrome。

---

## 1. 现象

线上 `/api/trends` 里，今日头条热搜几乎全部落 `no_source`（实测 4/5），
前端只能显示一行标题，事实抽取无米下锅。

## 2. 根因（两层，必须分开看）

### 2.1 线上必挂的一层：Railway 容器里没有 Chrome

原链路（`_fill_toutiao_fulltext` 的 A2）依赖：
`/trending/<id>` 是 JS 壳 → 无头渲染 → 从 DOM 里正则捞 `/article/<id>` → 取正文。

但容器里没装浏览器，`_chrome_available()` 恒为 False，整条 A2 **静默降级**。
本地能跑通纯粹是因为本机有 Chrome / CDP —— 「本地好、线上挂」的典型。

### 2.2 解法：换搜索引擎爬虫 UA，走头条的 SSR 分支

| UA | `/trending/<id>` 返回 |
|---|---|
| 普通 Chrome UA | 4.8KB **JS 壳**，无正文 |
| 搜索引擎爬虫 UA | 8–10KB **服务端渲染完整 HTML**，含「事件详情」区块 |

实测 4 个爬虫 UA（Baiduspider / Googlebot / bingbot / Sogou）行为**完全一致**，
所以只取一个，不搞 UA 轮换（轮换没有收益，只增加延迟）。

**⚠️ 关键纠错：这不是概率问题。** 一开始看到同一批页面时好时坏（6/11 ↔ 11/11）以为是限流，
于是对失败页连抓 10 次 —— 结果 0/10，完全稳定。
差异来自**话题本身的结构类型**，不是网络抖动。差一点就把「多试几次」当成解法。实测 0.3s/条。

## 3. 话题页的三种结构（决定能拿到什么）

「事件详情」区块里放什么，取决于该热点是文章、微头条，还是短视频：

| 类型 | 判据 | 实测正文量 | 处置 |
|---|---|---|---|
| **文章型** | 块内有 `href="/article/<id>"` | 741–3730 字 | 取文章全文 |
| **微头条型** | 块内有 `/w/<id>` | 292 字 | 取微头条正文 |
| **视频型** | 无外链，只有几十字视频文案 | 56–119 字 | **本身就没有文章正文** → 诚实标记 |

12 条样本分布：文章型 6 · 微头条型 1 · 视频型 4 · （另有 1 条真实短简讯）

> 视频型不是「抓取失败」。事件本身是一条短视频，全网就没有配套文章。
> 这时**不能拿视频文案冒充原文**去做事实抽取，只能如实标记。

## 4. 顺带查出并修掉的两个真 bug

### 4.1 中文源兜底「假溯源」（严重）

追踪时就地抓到：

```
热搜：国家卫健委：进一步营造生育友好环境            (2026-09-14)
兜底：国家卫健委发布新冠病毒疫苗第二剂次加强免疫接种实施方案  (2022-12)
匹配度 = 4
```

两边**只共有一个机构名「国家卫健委」**，事件毫无关系，却被当作「原文」配上去了，
前端还会显示成「新华网 · 时政（中文源兜底）」。

`cn_fallback_article()` 的注释里明确写着「宁可诚实标记无原文，也不给错的出处（伪造溯源比缺原文更糟）」，
但 `min_score=3` 没兜住这个 4 分案例 —— **实测正经匹配最高只到 1–2 分**，3 分这个阈值是失效的。

**修**：`min_score` 3 → 6。代价是 B 层基本不再命中（本就对突发热搜无用），
换来的是不再有错出处。

### 4.2 短正文被误挡 → 反而撞上假匹配

「上5休1上5休3…」133 字、「国家卫健委…」140 字，都是**真实且完整**的简讯（结尾有句号、
有「来源/编辑」署名），不是抓取截断。原阈值 150 把它们挡掉 → 掉落 B 层 → 才撞出 4.1 的假匹配。

实测边界很干净：

```
视频型文案： 56, 64, 67, 71, 75, 111, 119 字
真实正文  ：133, 140, 292, 724, ...  字
```

→ 阈值 `_TT_MIN_TEXT` 取 **125**：放行真实简讯，挡住视频文案。

## 5. 改动清单

文件：`backend/agent_reach_bridge.py`（3 批原子替换，共 20 项，全部命中）

| # | 位置 | 改动 |
|---|---|---|
| 1 | `fetch()` | 新增 `headers=None`，缓存键带上 UA（同一 URL 换 UA 内容不同，否则会互相顶掉） |
| 2 | 头条段注释 + 常量 | 新增 `BOT_UA` / `_TT_W_RE` / `_TT_BLOCK_RE` / `_TT_MIN_TEXT=125` |
| 3 | 新增 7 个函数 | `_tt_event_block` `_tt_block_text` `_tt_page_source` `toutiao_article_ssr_text` `toutiao_article_full` `toutiao_micro_text` `toutiao_topic_ssr_text` |
| 4 | `_fill_toutiao_fulltext` | A1 改用 `toutiao_article_full`；新增 **A2a（SSR，纯 HTTP）**；原渲染降为 **A2b** 并加 `_ssr_conclusive` 闸门 |
| 5 | 降级文案 | 按 `kind` 分型（视频型 / 短文案 / 未附正文），前端 tooltip 直接说清原因 |
| 6 | `cn_fallback_article` | `min_score` 3 → 6，注释补上假溯源案例 |

**A2a 闸门的作用**：话题页一旦解出「事件详情」块，答案就已确定，
不必再去尝试渲染 —— 否则在无 Chrome 环境会白跑并刷出误导性告警。

## 6. 验证

### 6.1 线上等价环境（最关键的证据）

本地起桥接层（端口 8799）跑整榜，日志里同样出现：

```
[warn] render.chrome.probe: 无头浏览器探测失败，将整体回退
[warn] render.chrome: 无头浏览器不可用：头条话题页无法渲染取原文
```

即**渲染路径全程未参与**，与 Railway 同构。结果：

| 指标 | 改造前（线上实测） | 改造后 |
|---|---|---|
| 头条 no_source | 4/5 | **3/10** |
| 可用正文（ok+short） | ≈0/5 | **7/10 条** |

> 剩下 3 条 no_source 全是**视频型**事件——本来就没有文章正文，不是抓取失败。

### 6.3 回归

- `fetch()` 全部 12 处调用点均为**关键字传参**（`timeout=`），签名扩展向后兼容，无位置参数风险。
- 其他源状态分布未受影响（CGTN / Variety / NPR / Global / Billboard 正常出 ok/short）。
- 短正文放行为 `short` 在前端只体现为「原文偏短」徽标 + tooltip 说明，**前端无需改动**。
