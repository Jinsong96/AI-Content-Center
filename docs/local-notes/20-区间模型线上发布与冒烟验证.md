## 3. 新暴露 / 新确认的问题

### 3.1 🔴 `事实一致性` 在 B2+ 三档判 fail —— **校验器误判，内容其实达标**

复现：B2+.1 / B2+.2 / B2+.3 三档的「事实一致性」全部 `fail`、`detail` 为空。

根因（读代码确认）：`GEN_VALIDATE_CODE` 用 `factcard` 里的**阿拉伯数字**做子串匹配 ——

```js
factNums = (JSON.stringify(JSON.parse(factcard||'{}')).match(/\d[\d,.]*%?/g) || []).slice(0,6);
const missNums = factNums.filter(n => !String(article||'').includes(n));
if (factNums.length && missNums.length === factNums.length) → fail
```

本素材事实卡里的数字序列只有 `["200"]`（"around 200 trees"）。而 **B2+ 三档把数字写成了英文单词**
（`two hundred trees` / `five degrees Celsius`）。子串匹配找不到 `"200"` → 判 fail。

机械核验内容层面的实际覆盖（`paras_json` 全文探针）：

| 档位 | two hundred | five degrees | summer | narrow | planting more trees |
|---|---|---|---|---|---|
| B2+.1 | ✅ | ✅ | ✅ | ✅ | ✅ |
| B2+.2 | ✅ | ✅ | ✅ | ✅ | — |
| B2+.3 | ✅ | ✅ | ✅ | ✅ | — |
| B1.1 | ✅(写作 `200`) | ✅ | ✅ | ✅ | ✅ |

⇒ **内容覆盖是完整的，判 fail 纯属校验口径缺陷**。B1 组因为写了阿拉伯数字 `200` 而侥幸通过。

**影响**：前端会把这 3 个 fail 当成真实失败呈现，用户看到 B2+ 三档"不合格"，会误判为生成质量崩了。

**建议修法（二选一，需教研/产品定口径）**：
- **(a) 校验器侧**：对 `factNums` 增加英文数词归一化（`200 ↔ two hundred`、`5 ↔ five`），再做匹配；
- **(b) 生成侧**：B1/B2+ 提示词明确要求「数字一律用阿拉伯数字写」，与事实卡逐字对齐。

> 倾向 (a)：这是**校验器过度严格**，不该让生成侧迁就一个脆弱的子串匹配。
> 且顺带说明：`slice(0,6)` 只取前 6 个数字、且要求**全部**缺失才 fail，口径本身就比较毛糙。

⇒ 再次确认：**区间下界不能"判定了算"，必须实测钉**（`docs/14` 设计的"实测校准"环节仍未实现）。
在实现校准之前，前端若按 `level_lo` 限制档位控件范围，会**给出一个不可靠的下界**。

### 3.7 `quiz_json` 偶发尾逗号 → 无清洗透传

首跑 MAIN 时 `quiz_json` 严格 `json.loads` 抛错：`Expecting ',' delimiter: line 1 column 12800`。
重跑即好（模型偶发尾逗号，与 `docs/19` 记录的聚合节点问题**同源**）。

值得注意：`quiz_json` 是 `nodeQuiz.text` **原样透传**（`outputs` 里直接绑 `["nodeQuiz","text"]`，
**没有经过任何清洗**）。⇒ 一旦模型写尾逗号，**前端拿到的就是一段无法解析的 JSON**，
表现为"没有题目"。聚合层那两个 `parseJSON` 已加容错，但 **`nodeQuiz` 这条路径漏了**。

**建议**：在 `nodeEnd` 前加一个轻量 code 节点，对 `quiz_json` / `gist_check_json` 做
"先严格后容错"的归一化（与聚合层同一套 `parseJSON`）。

> 顺带修了诊断脚本：`tools/dify_run_app.py` 原来把 `--out` 落盘写在 `summarize()` **之后**，
> 于是 summarize 里一个字段解析失败 → **整份 outputs 随进程一起丢掉**。
> 已改为「**先落盘、再打印摘要**」+ 容错解析 + 打印失败不中断。这个坑值得写进 skill。

## 6. 上线后报障：「AI 抽取失败：level in input form must be one of the following: [...]」

### 6.1 现象

前端第 03 步（事实抽取）点击后报：

```
AI 抽取失败：level in input form must be one of the following:
['A1.1','A1.2','A1.3','A2.1','A2.2','A2.3','B1.1','B1.2','B1.3','B2+.1','B2+.2','B2+.3']
```

### 6.2 定性：**不是生成失败，是入参在门口被打回**

复现（`dify_run_app.py --app=fact`）：

| 传入 | 结果 | 耗时 | tokens | 执行节点数 |
|---|---|---|---|---|
| `level=A1_1`（**前端现在传的格式**） | `failed` | **2.1s** | **0** | **0** |
| `level=A1.1`（工作流声明的格式） | `succeeded` | ~14s | ~3.2k | 全部 |
| 整个省略 `level` | `succeeded` | 19.4s | ~3.2k | 全部，自动判档 `A2.2–B1.1` |

⇒ 2.1 秒、0 token、0 节点 —— **工作流根本没启动**，没有消耗、没有产生脏数据。
这是 Dify 的 **start 节点 select 枚举入参校验**在入口拦下（即 skill 里的坑 6 同族）。

### 6.3 根因：前端与工作流的「档位取值格式」不一致

| 侧 | 取值格式 | 证据 |
|---|---|---|
| 前端 | **下划线式** `A1_1` / `B2P_1` | `frontend/index.html` L2279 `wfInputs = {..., level: state.lvl}`；`state.lvl` 来自 `subKeys()` / `LEVELS12[].key`，全是下划线键；`nkKey()` 把任意写法**归一化成下划线**，`nkDisp()` 才转点式（仅用于显示） |
| 工作流 | **点式** `A1.1` / `B2+.3` | FACT / GEN / MAIN 三个 `nodeStart` 的 `level` 都是 `select`，options 由生成器 `v['options'] = [L['d'] for L in LEVELS]` 写入（`L['d']` = display 点式） |

前端把**内部主键**直接当**对外枚举值**发了出去。`nkDisp()` 只用在渲染上，**没有用在入参上**。

### 6.4 责任归属：**不是 2026-09-14 这次发布引入的**

用 `GET /console/api/apps/{id}/workflows`（发布版本列表）逐版核对 FACT 的 `nodeStart.level` options：

| 发布版本（UTC） | 节点数 | `level` options | 备注 |
|---|---|---|---|
| 2026-09-02 08:47 | 10 | `['A2','B1','B2']` | 三档时代 |
| **2026-09-10 11:17** | 12 | **12 个点式** | 「12子档改造：事实抽取+敏感排查+12档分级」 |
| 2026-09-10 11:28 ~ 11:36 | 12 | 12 个点式 | 切渠道 / 清洗节点 |
| **2026-09-11 07:06:42** | 12 | **12 个点式** | A1.1/A1.2 词数放宽（**本次发布之前的线上版本**） |
| **2026-09-14 01:54:40** | 12 | **12 个点式** | 本次区间模型发布 |

⇒ **本次发布前后，`level` options 完全一样**（都是 12 个点式）。
⇒ 这个不匹配**从 2026-09-10 19:17（北京时间）「12子档改造」那次发布就存在**，
   本次区间模型发布**没有引入、也没有修复**它。

再补两条旁证：
- 区间模型那批 15 处改动全部落在 `nodeFact` / `nodeGrade` / `nodeClean` / 生成节点 / `nodeAgg` /
  `nodeValidate` / 新增 `nodeGistCheck`，**没有一处碰 `nodeStart`**（`docs/19` §2 清单可查）。
- 旧的三档版本会以同样的方式拒绝 `A1_1`（只是报错里列 `['A2','B1','B2']`），
  所以「前端传下划线键」这条在 09-10 就已经与工作流不兼容。

### 6.5 为什么现在才暴露

- 12 子档上线（09-10 19:17）之后，`state.lvl` 的取值就从 `A2/B1/B2` 变成了 `A1_1` 这类下划线键，
  从此前端这条 FACT 调用就**必然失败**。
- GEN 那一步**碰巧没炸**：它传的是 `level: fc.level || state.lvl`，而 `fc.level` 来自 FACT 的输出
  （实测是点式 `A2.2`），**顺手兜住了**。⇒ 一旦 `fc.level` 为空，GEN 会以完全相同的姿势失败。
- 所以这是**一条已经坏了 4 天的路径**，不是新问题。

### 6.6 修法（三选一，未擅自改）

| # | 方案 | 改哪里 | 优点 | 代价 |
|---|---|---|---|---|
| **A** | **前端发点式**：`level: nkDisp(state.lvl)` | `frontend/index.html` FACT 调用的 `wfInputs`（GEN 的 fallback 也要一起改） | 一行级改动；保住 select 的枚举校验；与工作流声明一致 | 需要动前端 + 走部署链路 |
| **B** | **start 的 `level` 改成 `paragraph`/`text`**，由 `nodeGrade` 内部归一化 | `tools/dify_build_graphs.py`（FACT/GEN）+ `build_main_graph.py` | 前端/后端/第三方怎么传都不炸 | 丢掉入参枚举校验；且要重跑拼装器 + 三个图重新发布 |
| **C** | **FACT 调用干脆不传 `level`** | 前端 | 与 start 标签「可选，空则由分级节点判定」的设计意图最一致（FACT 这一步本来就还没到定档） | 用户的档位偏好不再影响分级；GEN 那步的 `fc.level` 仍要保证是点式 |

> **倾向 A + C 组合**：FACT 这一步**不传 level**（交给分级节点自动判，符合原设计），
> 生成（GEN）那步传 `nkDisp(fc.level || state.lvl)`。既修好当下，也堵住 GEN 的同类隐患。
>
> ⚠️ 若选 A/C，**注意本地 `frontend/index.html` 与线上不是同一版**
> （本地 677159 字节 / md5 `4aad34a7…`；线上 677393 字节 / md5 `f279d340…`）。
> 直接改本地再传会**把线上版本整段回退** —— 必须先 `tools/fetch_sources.py` 拉线上源码再改。

## 7. 修复与上线（2026-09-14 · A + C 组合）

### 7.0 先破一个前提：**本地与线上其实是同一版**

§6.6 那条「本地 ≠ 线上」的警告**是误判**，此处更正。

线上 HTML 比本地多 234 字节，逐行比对后确认：**唯一差异是第 7 行**——
线上被 bridge 注入成 `<script>window.WB_API_BASE="";window.WB_CONFIG={…};</script>`（273 字符），
本地是 `<script src="config.local.js"></script>`（39 字符）。273 − 39 = **234，严丝合缝**。
归一化这一行后逐行比对，**5549 行零差异**。

⇒ 结论：本地 `frontend/index.html` **就是**线上源码，**不需要** `fetch_sources.py` 回拉。

## 8. 同批修掉的交付缺口：GEN 拿不到 `gist`（低档退化）

### 8.1 缺口

前端调 GEN 时只传 `{summary, facts_text, angle, level, style, facts_raw}` —— **没传 `gist`**。
而 GEN 的 `nodeClean` 有兜底：

```js
gist: String(gist || '').trim() || String(facts_text || ''),
```

⇒ 低档 A1/A2 的**「去数字大意拍」基准被替换成了完整事实卡**。
（上游 `nodeFact` 确实产出了 `gist`，FACT 的 outputs 里有，只是前端没接。）

这是**上一轮已批准功能的交付缺口**（区间模型的核心就是低档改用大意拍），不是新需求。

### 8.2 实测影响（同素材、同模型，唯一变量 = gist）

| 档位 | 不带 gist | 带 gist | 规格区间 |
|---|---|---|---|
| A1.1 | 86 | 92 | 60–110 |
| A1.2 | **119** | 149 | 90–140 |
| A1.3 | **134** | 180 | 120–160 |
| A2.1 | 218 | 236 | 150–200 |
| A2.2 | 225 | 295 | 180–250 |
| A2.3 | 266 | 347 | 250–300 |
| B2+.2 | **634** | 719 | 700–900 |
| B2+.3 | **665** | 915 | 900–1200 |

- **低档系统性欠写**（粗体为越界项）
- 校验：不带 gist **3 个硬失败**（蓝思 ×2 / 长度 ×1）→ 带 gist **0 个硬失败**
- 低档 `gist_map` 审计：不带时只引用到第 **4** 条 → 带时 **1–8 条**（符合「8 条大意」设计）
- 低档正文数字数：两者**均为 0**（提示词层的「不得出现数字」约束独立生效，这条没坏）

> 也就是说：**不是硬故障，而是质量退化**。不带 gist 时功能"能跑"，但低档写不到应该的长度与颗粒度。

### 8.3 修法（2 处）

| 位置 | 改法 |
|---|---|
| `applyLive()` 的 `state.factsCache` | 增加 `gist: o.gist \|\| ""` |
| `runGeneration()` 的 `wfInputs` | 增加 `gist: fc.gist \|\| ""` |

运行时候验证：GEN 请求体已含 `"gist": "..."` ✅

### 8.4 线上完整链路 e2e（真实登录 → FACT → GEN）

用**穿透式记录器**（挂在 `window.fetch` 上记录请求体、但照常转发真实请求）抓到的实况：

```
FACT 请求体  { material, style }                        ← level 已不传
FACT 输出    level=A2.2  lo=A2.2  hi=B1.1  info_points=4  gist=598 字符
state.factsCache = { has:true, gist_len:598, level:"A2.2" }   ← gist 缓存成功

GEN  请求体  { angle, facts_raw, facts_text, gist, level:"A2.2", style, summary }
             ↑ 含 gist(598 字符)    ↑ 点式
GEN  输出    articles=12  quizzes=36  checks=87/96  gist_check=pass
```

**12 档文章 + 36 题全部产出，⑨ 大意复核 pass，请求体契约与设计完全一致。**

> （`runGeneration()` 收尾会 `state.live.run = data`，注意它还顺手用 GEN 的响应
> 又跑了一次 `applyLive()` —— 同样会覆盖 `state.factsCache`。）
