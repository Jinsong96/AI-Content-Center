# 扩展难度档位指南（A1/A2/B1/B2/C1）

> 面向：后端工程师 / 产品经理
> 场景：当前系统支持 **A2 / B1 / B2** 三档，若需扩展为 **A1 / A2 / B1 / B2 / C1** 五档

---

## 0. 结论先行

**⚠️ 增加难度档位不是"跟后端说一声"就能完成的改配置工作，它牵动 Dify、前端、后端三处，且 Dify 是改动最大、风险最高的部分。**

| 层 | 改动量 | 风险 |
|----|--------|------|
| **Dify 工作流** | 🔴 大（核心 AI 逻辑） | 🔴 高（段落对齐质量 + 生成耗时） |
| **前端 demo** | 🟠 中（约 11 处硬编码 + CSS 布局） | 🟡 中（五栏布局会很挤） |
| **后端** | 🟢 小（枚举扩展 + 参数校验） | 🟢 低 |

---

## 1. Dify 改动（🔴 最大工作量）

### 1.1 必改项清单

| # | 位置 | 改动内容 |
|---|------|---------|
| 1 | **nodeStart `level` 变量** | 若为 select 枚举，需加入 `A1` / `C1` 选项 |
| 2 | **nodeGenAll 提示词** ★ | ①输出 JSON 结构从 `{title, A2[], B1[], B2[], words}` 扩展为 `{title, A1[], A2[], B1[], B2[], C1[], words}`<br>②补充 A1、C1 的难度规范（词数/句长/词汇量/语法/生词表条数） |
| 3 | **nodeGenAll `max_tokens`** | 当前 `8000`。五档输出 token 约增 67%，**必须上调**（建议 ≥12000，并实测验证不截断） |
| 4 | **nodeAgg（解析节点）** | 解析新增的 `A1` / `C1` 字段，输出 `article_a1` / `article_c1` / `paras_a1` / `paras_c1` |
| 5 | **nodeValidate（校验节点）** | 长度/句长/词汇规则字典加入 A1、C1 两档：当前 `LEN = {A2:[120,250], B1:[150,300], B2:[180,350]}`，`SLEN = {A2:12, B1:18, B2:25}` |
| 6 | **nodeEnd 输出变量** | 新增 `article_a1` / `article_c1` / `paras_a1` / `paras_c1` |
| 7 | **知识库（分级标准）** | 补充 A1、C1 的词汇/句长/语法/篇幅规范（`output/dify_kb_backup/分级标准.md`） |

### 1.2 ★ 核心风险：段落对齐质量

**当前机制**：`nodeGenAll` 用**单个 LLM 节点一次生成三档**，在提示词中强制：
- 三档正文都**恰好 4 段**
- 各段主题**固定顺序**（第1段引入 / 第2段主体 / 第3段细节 / 第4段收尾）
- 输出严格 JSON，段落天然一一对应

**为什么这是当前设计**：早期曾用三个独立 LLM 分别生成 A2/B1/B2，导致段落数量不一致、同序号语义不对应、出现空段。合并为单次生成后才解决（详见 `03-dify-workflows.md` 第 3 节）。

**扩展为五档的风险**：

| 风险 | 说明 |
|------|------|
| **对齐难度陡增** | 模型需同时维持 5 档 × 4 段 = **20 个段落**的语义对应（当前是 12 个）。档位越多，维持"同序号语义一致"越难，可能出现部分档位错位 |
| **输出长度** | 五档全文 + 生词表，token 约增 67%，有超出 `max_tokens` 被截断的风险（截断会导致 JSON 解析失败，全流程报错） |
| **生成耗时** | 当前约 22–30s。五档预计 **40–60s**，已远超同步请求的合理范围，**生产必须异步化** |
| **质量波动** | 档位增多时，中间档（B1/B2）的质量可能被稀释 |

### 1.3 建议方案（三选一）

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A. 直接扩展为五档一次生成** | 改提示词 + 上调 max_tokens | 改动最小，复用现有架构 | 对齐质量与耗时风险最高，需大量实测 |
| **B. 锚定档 + 派生（推荐）** | 先生成中间档（B1/B2），再以它为锚派生 A1/A2（简化）与 C1（深化） | 对齐更稳（派生时以锚定档段落为单位改写，天然对齐），单档生成快、可并行 | 需新增派生节点，工作流更复杂；token 总量增加 |
| **C. 分档生成** | 按档位分组（A1+A2 / B1+B2 / C1），组内保持对齐 | 折中，单次输出量可控 | 组间对齐需额外保证；流程更长 |

> **产品建议**：若五档是长期规划，建议采用 **方案 B**。它把"生成"与"改写"解耦，后续增删档位只需调整派生规则，不动核心生成节点。

| 1317 | `const pk = { A2: o.paras_a2, B1: o.paras_b1, B2: o.paras_b2 }` | 段落输出映射，**需加 paras_a1 / paras_c1** |

| 2769 | `const lv=["A2","B1","B2"]` | 档位切换逻辑 |

### 2.2 CSS 布局（必须改，否则显示挤爆）

```css
/* 当前：三栏 */
.pcols{display:grid;grid-template-columns:1fr 1fr 1fr;gap:14px}
.alignrow{display:grid;grid-template-columns:44px 1fr 1fr 1fr;gap:10px}
```

五档需改为（以 alignrow 为例）：
```css
.alignrow{display:grid;grid-template-columns:44px repeat(5,minmax(0,1fr));gap:8px}
```

⚠️ **体验问题**：五栏并排在 1440px 宽度下每栏仅约 240px，阅读体验差。建议改为：
- **主档 + 切换模式**：默认展示当前选中档位，可切换对比（推荐）
- 或保留并排但支持横向滚动

## 3. 后端改动（🟢 较小）

| 项 | 改动 |
|----|------|
| `level` 枚举 | `A2/B1/B2` → `A1/A2/B1/B2/C1`（请求参数校验、数据库字段长度） |
| 数据模型 | `articles` / `paragraphs` 表的 `level` 字段（VARCHAR(4) 即可容纳）；`generations.level` 同理 |
| 生成任务 | 参数校验白名单扩展 |
| 异步化 | 五档生成耗时预计 40–60s，**强烈建议改为异步任务**（原三档 20–30s 同步已勉强） |

> 详见 `04-data-model.md`。

---

## 4. 建议的推进顺序

1. **先在 Dify 上做可行性验证**（最关键）：改一个测试工作流，用五档提示词跑 5–10 篇不同素材，检查：
   - JSON 是否被截断（max_tokens 是否够）
   - 五档段落是否全部对齐（同序号语义是否对应）
   - 生成耗时是多少
   - 各档质量是否达标（尤其 B1/B2 是否被稀释）
2. **根据验证结果决定方案**：若方案 A（一次五档）质量达标就用 A；若对齐不稳定，改用方案 B（锚定档 + 派生）。
3. **再改前端**：先改数据层（SPECS / LVL_META / 映射），最后调布局。
4. **后端同步**：枚举扩展 + 异步化。

---

## 5. 一句话总结

> 加档位 = **Dify 提示词与节点改造（大头）+ 前端 11 处硬编码与布局改造（中）+ 后端枚举扩展（小）**。
> 其中**段落对齐质量**和**生成耗时**是两个必须先验证的技术风险，建议在承诺排期前先做 Dify 侧的可行性验证。
