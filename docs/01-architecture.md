# WorkBuddy AI 内容生产平台 · 系统架构与资产清单

> 面向：后端工程师
> 版本：v1.0（demo 交接版）
> 日期：2026-09-01
> 状态：**当前为可运行 demo，需工程化改造后方可上线**

---

## 1. 项目定位

**AI 驱动的英文分级阅读内容生产平台**。核心能力：把中文/英文素材，通过 AI 工作流一键生成 **A2 / B1 / B2 三档 CEFR 分级英文文章**，且三档段落**逐段语义对齐**（读者可在阅读中自由切换难度而不丢失阅读位置），经人工校对与审核后入库，最终对接内容管理平台。

**产品名**：WorkBuddy（内部代号）
**核心用户**：英语学习内容生产团队（市场 / 教研 / 审核三类角色）

| # | 资产 | 位置 | 规模 | 说明 |
|---|------|------|------|------|
| 1 | 前端（单文件） | `output/frontend/index.html` | 2789 行 | **全部 UI + 业务逻辑 + 状态管理**，无构建、无框架，浏览器直接打开 |
| 2 | 后端桥接层 | `output/backend/agent_reach_bridge.py` | 587 行 | 零第三方依赖（纯 Python 标准库），负责真实热点抓取与翻译 |
| 3 | Dify 工作流 ×2 | Dify Cloud（**不在代码库内**） | — | 核心 AI 编排逻辑，见 `03-dify-workflows.md` |
| 4 | 知识库备份 | `output/dify_kb_backup/` | 2 个 .md | 分级标准、敏感内容规则（Dify 知识库原始文本） |
| 5 | 素材库 | `material/` | 1163 文件 | 576 txt / 529 png / 53 md / 5 pdf（公版书等素材源） |

### 2.1 前端单文件包含什么

`index.html` 是一个自包含的单体应用，内联了：

- **13 步业务流程的完整 UI**（素材入口 → 内容库）
- **状态管理**：全局 `state` 对象（当前步骤、选中热点、生成结果、内容库等）
- **AI 调用**：直连 Dify App API（阻塞模式）
- **内容库**：基于 `localStorage`（键 `wb_content_bank_v1`）
- **封面生成**：直连硅基流动文生图
- **朗读**：浏览器原生 `speechSynthesis`（英音/美音）
- **双语 i18n**：所有文案走 `L(中文, 英文)` 函数

⚠️ **这意味着前端没有任何模块化**，工程化时需要整体拆分为组件 + 状态管理 + API 层。

## 3. 系统架构

### 3.1 当前架构（demo）

```
┌─────────────────────────────────────────────────────────┐
│                     浏览器（前端）                         │
│  index.html  2789 行单体                                  │
│  ├─ 13 步流程 UI                                          │
│  ├─ state（内存状态）                                      │
│  ├─ localStorage（内容库 wb_content_bank_v1）              │
│  └─ 直连外部 API（密钥硬编码 ⚠️）                          │
└─────────────────────────────────────────────────────────┘
        │                    │                    │
        ▼                    ▼                    ▼
┌──────────────┐  ┌──────────────────┐  ┌──────────────┐
│  Dify Cloud  │  │  硅基流动         │  │ 本地桥接层    │
│  2 个工作流   │  │  文生图 + 翻译    │  │ 8787（本机）  │
│              │  │                  │  │ RSS/头条抓取  │
└──────────────┘  └──────────────────┘  └──────────────┘
```

**关键特征 / 问题**：
1. **无后端业务服务**：前端直连所有外部 API，密钥暴露在前端源码中。
2. **无数据库**：内容库存 `localStorage`，换浏览器/设备即丢失，多用户无法共享。
3. **桥接层只在本机运行**：`AGENT_REACH_API = http://127.0.0.1:8787`，他人访问部署链接时连不上（且 HTTPS 页面访问 localhost 会被 Chrome 私有网络访问策略拦截，已加 `Access-Control-Allow-Private-Network` 头缓解）。
4. **Dify 挂在个人账号**：生产需迁移到团队/服务账号。

### 3.2 目标架构（工程化）

```
┌──────────────┐
│   前端        │  React/Vue 组件化，只与自家后端通信
└──────┬───────┘
       │ HTTPS / JSON  （携带 JWT）
       ▼
┌────────────────────────────────────────────────────────┐
│                  后端服务（新建，核心工作量）              │
│  ┌─────────┬─────────┬─────────┬─────────┬──────────┐  │
│  │ 认证鉴权 │ 素材/热点│ 生成编排 │ 内容库  │  审核流   │  │
│  │  RBAC   │ 信源管理 │ Dify 代理│ 推送    │          │  │
│  └─────────┴─────────┴─────────┴─────────┴──────────┘  │
│  ┌──────────────────────────────────────────────────┐  │
│  │  任务队列（生成是长时间任务，必须异步化）            │  │
│  └──────────────────────────────────────────────────┘  │
└───────┬──────────────┬──────────────┬─────────────────┘
        │              │              │
        ▼              ▼              ▼
   ┌─────────┐   ┌──────────┐   ┌──────────┐
   │  数据库  │   │  Redis    │   │ 对象存储  │
   │(PostgreSQL)│ │ 缓存/队列 │   │ 封面图    │
   └─────────┘   └──────────┘   └──────────┘
        │
        ▼  对外调用（密钥全部服务端化）
   ┌─────────────────────────────────────────┐
   │ Dify Cloud │ 硅基流动 │ 新闻源 RSS/热榜  │
   └─────────────────────────────────────────┘
```

## 4. 业务流程（13 步 / 3 阶段）

| 阶段 | 步骤 | 名称 | 说明 |
|------|------|------|------|
| **P1 内容生成与校验** | 01 | 素材入口 | 三条入口：热点搜集 / 自有版权 / 公版书 |
| | 02 | 热点搜集 | Agent-Reach 真实抓取（头条热榜 + HN + RSS），支持主题/子主题筛选、自定义信源 |
| | 03 | 敏感排除 | S0–S3 分级，S0 直接排除（**在 Dify 工作流内完成**） |
| | 04 | 选题标签 | 六大主题 × 子主题，系统智能推荐 + 人工多选 |
| | 05 | 事实抽取 | AI 抽取原子化事实卡（中英对照 + 置信度 + 交叉验证） |
| | 06 | 分级标准 | A2/B1/B2 词表、句长、语法、篇幅规范（知识库版本化） |
| | 07 | 内容生成 | 三档生成 + 写作风格（默认 + 7 位名人） |
| | 08 | 校验与身份 | 8 项质量校验 + Content ID 身份记录 |
| **P2 内容切分** | 09 | 段落切分 | 三档段落对齐展示（**在 Dify 内由 nodeGenAll 保证对齐**） |
| | 10 | 人工校对 | 逐段校对，可编辑 |
| | 11 | 对齐确认 | 确认对齐结果 |
| **P3 审核与入库** | 12 | 逐段审核 | 逐段审核，通过/驳回 |
| | 13 | 内容库 | 已入库文章列表，支持查看/删除/推送至内容管理平台 |

### 4.1 关键数据流（生成链路）

```
选素材
  │
  ▼
startLiveRun(material, level, style)
  │
  ├─ 首次生成 → 完整工作流（app-RVTU8k…）
  │     输入：material / level / style
  │     输出：article_a2|b1|b2, paras_*, para_count,
  │           validation_*, title, summary, angle, facts_text, facts_raw
  │     ⏱ 约 22–30 秒
  │
  └─ 换风格（有 factsCache）→ 生成专用工作流（app-SuBV84…）
        输入：summary / facts_text / angle / level / style / facts_raw
        跳过事实抽取/敏感排查/分级，只重跑生成 + 校验
        ⏱ 约 15–20 秒
```

**重要**：前端在首次生成后会缓存 `facts`（`state.factsCache`），后续换风格时直连"生成专用"工作流以提速。这是已有的拆分优化，工程化时应保留该设计。

## 7. 工程化改造范围

### 7.1 必须新建（后端业务服务）

| 模块 | 工作量 | 说明 |
|------|--------|------|
| 用户认证 + RBAC | 3–4 天 | 用户表、JWT/会话、三级权限 |
| 素材与信源管理 | 3–5 天 | 信源 CRUD（按 user_id）、定时抓取、去重、缓存 |
| 生成编排（Dify 代理） | 3–5 天 | 封装 Dify 调用、**异步任务化**（生成 20–30s，不能同步阻塞） |
| 内容库 + 推送 | 3–4 天 | 文章/段落/事实卡入库，对接内容管理平台接口 |
| 审核流 | 2–3 天 | 审核状态机、记录留痕 |
| 数据库与迁移 | 3–4 天 | 见 `04-data-model.md` |
| 前端工程化 | 5–8 天 | 拆分组件、接真实 API、登录鉴权、状态管理 |

### 7.2 可复用 / 低改造

- ✅ **Dify 两个工作流**：核心 AI 逻辑已跑通，基本可直接使用（但需迁移到团队账号）
- ✅ **后端桥接层的抓取逻辑**：RSS 解析、头条热榜解析、翻译、分类的 Python 代码可直接复用，只需：
  - 包一层 HTTP 服务（已有 `http.server` 雏形）
  - 加数据库持久化、鉴权、限流、错误处理
- ✅ **知识库文本**（分级标准 / 敏感规则）：可直接导入
- ✅ **业务流程与 UI 设计**：13 步流程已验证，可直接作为产品原型参照

### 7.3 必须废弃

- ❌ 前端 `index.html` 中的密钥硬编码 → 全部移服务端
- ❌ `localStorage` 内容库 → 改数据库
- ❌ 前端直连 Dify / 硅基流动 → 改为后端代理
- ❌ 前端模拟的角色登录 → 真实鉴权

## 8. 已知债务与风险（⚠️ 交接重点）

| # | 风险 | 严重度 | 说明 |
|---|------|--------|------|
| 1 | **密钥全在前端源码** | 🔴 高 | Dify key ×2、硅基流动 key，公开可访问 |
| 2 | **数据在 localStorage** | 🔴 高 | 换设备丢失，多用户不共享 |
| 3 | **Dify 挂个人账号** | 🔴 高 | 生产不可用，必须迁团队/服务账号 |
| 4 | **生成是同步阻塞调用** | 🟠 中 | 20–30s 同步请求，生产需改异步任务 + 轮询/SSE |
| 5 | **桥接层仅本机** | 🟠 中 | 他人无法使用；且 HTTPS→localhost 有 PNA 拦截 |
| 6 | **头条热点无正文** | 🟠 中 | 只有标题，素材单薄；当前用 AI 摘要兜底 |
| 7 | **主题分类为关键词启发式** | 🟡 低 | 偶有误判（如"币"裸词误匹配"纸币"） |
| 8 | **demo 含模拟数据** | 🟡 低 | 内置 20 条热点、用户兴趣榜均为写死的演示数据 |
| 9 | **无测试、无监控、无限流** | 🟠 中 | 上线前需补齐 |
| 10 | **翻译慢** | 🟡 低 | 硅基流动单条 ~9s，靠磁盘缓存缓解，生产建议换更快方案 |
