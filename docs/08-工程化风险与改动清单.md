### P0-3　业务数据 100% 存浏览器 localStorage，无服务端持久化

**证据**：5 个持久化 key，直接读写 `localStorage` 共 **12 处**（6 个 `setItem` + 6 个 `getItem`）：

| Key | 内容 |
|---|---|
| `wb_content_bank_v1` | 内容库文章 |
| `wb_material_bank_v1` | 素材库 |
| `wb_publish_history_v1` | 发布记录 |
| `wb_feedback_data_v1` | 用户反馈 |
| `wb_taxonomy_v1` | 标签体系缓存 |

**后果**：
- 每个人打开的都是一个**空系统**，A 生成的文章 B 看不到
- 清除浏览器缓存 = 数据全丢，无任何备份
- 封面以 base64 存 localStorage，512×512 约 **0.55 MB/张**，浏览器上限约 5 MB → **约 9 张就写满**（现有 `pruneCoverQuota()` 只是打补丁）

**改造量评估（已实测）**：

| 项 | 数量 |
|---|---|
| 持久化函数 | 8 个（`loadBank` / `saveBank` / `loadMaterialBank` / `saveMaterialBank` / `loadPublishHistory` / `savePublishHistory` / `initFeedbackData` / `loadTaxonomy`） |
| 调用点 | **56 处** |
| 直接碰 localStorage | **仅 12 处**（封装得不错） |

**⚠️ 关键陷阱**：`fetch` 天然异步。若直接把 `loadBank()` 改成 `async`，**56 个调用点全部要加 `await`**，改造量与回归风险都会暴涨。

**推荐的过渡设计（可让前后端并行开发，互不阻塞）**：

```
内存缓存 + 同步签名
  ├─ 应用启动时异步拉一次全量进内存 state
  ├─ loadX()  直接返回内存副本（保持同步签名 → 56 个调用点零改动）
  └─ saveX()  写内存 + 异步 PATCH 到服务端（失败则标记为「未同步」并提示）
```

后端接口就绪后，只需改这 8 个函数的**内部实现**，页面代码完全不动。

**负责人**：后端（建库 + API）+ 前端（8 个函数内部）

### 关于第 2 项：如何导出数据样本

在你**平时使用平台的那个浏览器**里打开线上链接，F12 → Console，粘贴执行：

```javascript
const keys = ["wb_content_bank_v1","wb_material_bank_v1","wb_publish_history_v1","wb_feedback_data_v1","wb_taxonomy_v1"];
const out = {};
keys.forEach(k => { try { out[k] = JSON.parse(localStorage.getItem(k) || "null"); } catch(e) { out[k] = "PARSE_ERROR"; } });
console.log(JSON.stringify(out, null, 2));
// 如需下载：
const blob = new Blob([JSON.stringify(out)], {type:"application/json"});
const a = document.createElement("a");
a.href = URL.createObjectURL(blob); a.download = "readpal_sample_data.json"; a.click();
```

> ⚠️ 注意：导出的样本里**包含封面 base64**，文件可能较大（几十 MB）。给后端时可只保留 2–3 篇代表性文章，或先剔除 `coverDataUrl` 字段。

## 5. 需要拍板的产品决策（对接会上讨论）

### 决策 1：服务端抓取被反爬怎么办？⭐ 最重要

**背景**：`agent_reach_bridge.py` 现在能抓到头条等站点的正文，是因为它用的是**你本机的真实 Chrome + 你的网络环境**。搬到服务器后，headless 浏览器大概率被识别并拦截，抓取成功率会显著下降。

| 选项 | 成本 | 覆盖度 | 风险 |
|---|---|---|---|
| A. 加代理池 | 中（持续费用） | 高 | 合规需评估 |
| B. 改用 RSS / 官方 API | 低 | 低（部分源无 RSS） | 数据源收窄 |
| C. 白名单可信源 | 低 | 中 | 需要人工维护源列表 |
| D. 接受降级，抓取失败就走人工录入 | 最低 | — | 产品体验下降 |

**建议**：C + D 起步（成本低、合规风险小），A 视演示数据需求再上。**这个必须在后端动手前定下来**，否则做完了才发现抓不到，返工成本很高。

### 决策 2：Dify 继续用 Cloud 还是自托管？

- **Cloud**：省事，但 app key 有配额限制，且数据出网（涉及内容合规）
- **自托管**：可控、无配额，但需要运维投入

### 决策 3：素材原文全文存哪里？

当前 `material.text` 与 `material.originalText` 是大文本字段（单篇可达数万字符），且文章对象里还存了一份快照。

- 存数据库 TEXT 字段：简单，但表膨胀快
- 存对象存储：库里只存引用，但多一跳

### 决策 4：是否保留「多文风」特性？

当前支持 8 种文风（海明威 / 朱自清 / 欧·亨利 / 马克·吐温 / 村上春树 / 鲁迅 / 莎士比亚 / 默认）。每增加一种文风，Dify 生成工作流的复杂度与 token 消耗都会上升。确认这个特性是否进入正式版。

## 8. 已验证的历史坑位（提醒后端别重踩）

1. **Dify 状态字符串**：必须写成兼容集合 `exclude | excluded | block | reject`，不要只判一个值
2. **SiliconFlow 模型选择**：`Qwen3.6` / `DeepSeek-V4` 是推理模型，输出在 `reasoning_content` 而 `content` 为空。**选带 `Instruct` 后缀的**
3. **图床 URL 1 小时失效**：返回 URL 带 `X-Amz-Expires=3600`，必须立即下载转存
4. **写死带版本的工具路径迟早失效**：曾把 node 路径写死成 `22.22.2`，实际是 `22.22.2-2`，导致整条兜底链路**静默失效**（不报错、只是不工作）。路径探测一律用 glob + 兜底 PATH
5. **「抓取失败」与「没有数据」必须区分**：UI 上要能看出是源挂了还是真的没内容，否则运维无法判断
6. **绝不伪造内容**：历史上曾出现「用 LLM 编造的摘要冒充原文」的情况，导致事实抽取建立在幻觉之上。这是产品红线
